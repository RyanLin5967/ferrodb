CONCURRENT BRANCH MANAGEMENT DOES NOT MERELY FAIL TO SCALE — IT COLLAPSES.
  disjoint: 159.6 -> 118.8 -> 70.3 -> 41.4 -> 12.5 merges/sec across 1,2,4,8,16 threads.
  Monotone, every step down, ending at x0.08 — SIXTEEN THREADS DO ONE THIRTEENTH THE WORK OF ONE.
  The prediction in this file's header said FLAT. Flat would have been the good outcome.

⛔ THE PREDICTION WAS WRONG IN THE DIRECTION THAT MATTERS, and that is recorded rather than
smoothed: a global lock alone predicts FLAT (serialised, no worse than one thread). A monotone
COLLAPSE is the signature of a convoy — threads queueing, each acquisition paying for the queue —
or of work whose cost grows with the number of concurrent participants. Flat and collapsing are
different mechanisms and only one of them was predicted.

THE CONFOUND THAT WOULD HAVE KILLED THIS ROW, EXCLUDED BY THE COUNTS THEMSELVES
  More threads create more branches, and this repo has KNOWN O(open sessions) and
  O(removed x sessions) paths on the merge/reap side (ledger row W4). So the 16T point could have
  been slow because of accumulated branches rather than concurrency — the classic case of the
  harness being the wall. It is not, and the raw counts say so:
      1T  completed 320 cycles in the window   -> ~320 branches accumulated
     16T  completed  25 cycles in the window   -> ~25 branches accumulated
  The FASTEST point carried THIRTEEN TIMES MORE accumulated state than the slowest. Accumulation
  cannot explain a collapse that runs the other way. No extra control run was needed; the
  measurement already contained its own.

OVERSUBSCRIPTION IS ALSO EXCLUDED AS THE MAIN TERM. 16 harness threads plus ~17 of other load on
18 cores is roughly 2x oversubscribed, which costs about 0.5x. The observed 0.08x is fifteen times
past what that explains.

⚠ THE SHARED ARM IS NOT A RESULT, AND ITS "RECOVERY" IS A HARNESS FLAW I AM NAMING RATHER THAN
QUOTING. shared goes 1.00 -> 0.90 -> 0.66 -> 0.54 -> 0.87, recovering at 16T. A merge that is
QUARANTINED returns Ok, and this harness counts `exec("MERGE;").is_ok()` — so at 16 threads, where
every agent writes the same 16 ids, merges increasingly quarantine INSTEAD of applying, and a fast
refusal is counted as a completed cycle. The shared column measures how quickly merges can fail.
⇒ DO NOT QUOTE THE SHARED ARM. The disjoint arm is the clean one: there, merges genuinely apply.
⇒ Fixing it means counting `report.applied_to_target`, not `is_ok()`. Next revision of the harness.

WHAT THIS LOCALISES, AND WHAT IT DOES NOT
  ✓ It is not conflict detection: the disjoint arm has no two branches touching the same row.
  ✓ It is not branch accumulation: excluded above, by the counts.
  ✓ It is not oversubscription: off by fifteen.
  ⇒ It is something SHARED AND SERIAL on the merge path whose cost RISES with concurrency.
  ⛔ The obvious suspect is `pgwire/mod.rs:64` `Mutex<Catalog>`, which every `&mut Catalog` taker
     acquires and which DRAINS THE READERS on the way in — but that is a HYPOTHESIS READ OFF THE
     SOURCE, not a measurement. A profile of the 16T disjoint point is what names it, and until
     that exists the honest statement is "shared and serial", not "the catalog mutex".

WHY THIS ROW MATTERS MORE THAN THE ONES ABOVE IT: D56-D59 took the READ path to x8.12 at 16
threads. D61 measured per-branch SPACE to 10^6. D65 measured REOPEN to 10^6. Those are the three
places this project has looked, and all three are healthy. BranchBench's finding names "concurrent
branch management", and this is the first time that has been measured here. It is the only
structural wall currently on the board.
