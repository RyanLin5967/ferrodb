CONCURRENT BRANCH MANAGEMENT DOES NOT MERELY FAIL TO SCALE — IT COLLAPSES.
  disjoint: 159.6 -> 118.8 -> 70.3 -> 41.4 -> 12.5 merges/sec across 1,2,4,8,16 threads.
  Monotone, every step down, ending at x0.08 — SIXTEEN THREADS DO ONE THIRTEENTH THE WORK OF ONE.
  The prediction in this file's header said FLAT. Flat would have been the good outcome.

⛔ THE PREDICTION WAS WRONG IN THE DIRECTION THAT MATTERS, and that is recorded rather than
smoothed: a global lock alone predicts FLAT (serialised, no worse than one thread). A monotone
COLLAPSE is the signature of a convoy — threads queueing, each acquisition paying for the queue —
or of work whose cost grows with the number of concurrent participants. Flat and collapsing are
different mechanisms and only one of them was predicted.

THE CONFOUND THAT WOULD HAVE KILLED THIS ROW, EXCLUDED BY THE COUNTS THEMSELVES
  More threads create more branches, and this repo has KNOWN O(open sessions) and
  O(removed x sessions) paths on the merge/reap side (ledger row W4). So the 16T point could have
  been slow because of accumulated branches rather than concurrency — the classic case of the
  harness being the wall. It is not, and the raw counts say so:
      1T  completed 320 cycles in the window   -> ~320 branches accumulated
     16T  completed  25 cycles in the window   -> ~25 branches accumulated
  The FASTEST point carried THIRTEEN TIMES MORE accumulated state than the slowest. Accumulation
  cannot explain a collapse that runs the other way. No extra control run was needed; the
  measurement already contained its own.

OVERSUBSCRIPTION IS ALSO EXCLUDED AS THE MAIN TERM. 16 harness threads plus ~17 of other load on
18 cores is roughly 2x oversubscribed, which costs about 0.5x. The observed 0.08x is fifteen times
past what that explains.

⚠ THE SHARED ARM IS NOT A RESULT, AND ITS "RECOVERY" IS A HARNESS FLAW I AM NAMING RATHER THAN
QUOTING. shared goes 1.00 -> 0.90 -> 0.66 -> 0.54 -> 0.87, recovering at 16T. A merge that is
QUARANTINED returns Ok, and this harness counts `exec("MERGE;").is_ok()` — so at 16 threads, where
every agent writes the same 16 ids, merges increasingly quarantine INSTEAD of applying, and a fast
refusal is counted as a completed cycle. The shared column measures how quickly merges can fail.
⇒ DO NOT QUOTE THE SHARED ARM. The disjoint arm is the clean one: there, merges genuinely apply.
⇒ Fixing it means counting `report.applied_to_target`, not `is_ok()`. Next revision of the harness.

WHAT THIS LOCALISES, AND WHAT IT DOES NOT
  ✓ It is not conflict detection: the disjoint arm has no two branches touching the same row.
  ✓ It is not branch accumulation: excluded above, by the counts.
  ✓ It is not oversubscription: off by fifteen.
  ⇒ It is something SHARED AND SERIAL on the merge path whose cost RISES with concurrency.
  ⛔ The obvious suspect is `pgwire/mod.rs:64` `Mutex<Catalog>`, which every `&mut Catalog` taker
     acquires and which DRAINS THE READERS on the way in — but that is a HYPOTHESIS READ OFF THE
     SOURCE, not a measurement. A profile of the 16T disjoint point is what names it, and until
     that exists the honest statement is "shared and serial", not "the catalog mutex".

WHY THIS ROW MATTERS MORE THAN THE ONES ABOVE IT: D56-D59 took the READ path to x8.12 at 16

branch management", and this is the first time that has been measured here. It is the only

=== PROFILE — THE SHARED SERIAL THING, NAMED ==============================================
[HERE] `sample` over 25 s of a 40 s single-point run, 16 threads, DISJOINT arm.
Raw profile banked beside this file as d67_profile_16T_disjoint.sample.txt.
The point sustained 23.0 merges/sec over 40 s against 159.6 at one thread, so the collapse is
not an artifact of the sweep's 2-second windows — it reproduces over a long steady state.

  worker-thread samples (thread_start)                              316,396   100.0%
  ServerContext::catalog -> Mutex::lock -> __psynch_mutexwait       296,691    93.8%
  execution::executor::run  (ALL the actual work)                    20,538     6.5%

⇒ **93.8% OF ALL WORKER TIME IS BLOCKED WAITING FOR ONE MUTEX.** The previous section said the
wall was "something shared and serial" and refused to name it because the candidate had only been
read off the source. It is now measured, and it is the candidate: `pgwire/mod.rs:64`
`pub catalog: Mutex<Catalog>`, entered through `ServerContext::catalog()`.

That also settles the shape question the collapse raised. A plain serialised critical section
predicts FLAT; what makes it COLLAPSE is that `catalog()` does more than take a lock — it calls
`drain_readers()` on every acquisition, a scan over live connections, so the cost of ACQUIRING
rises with the number of participants. Sixteen agents do not merely queue, they make each other's
acquisitions more expensive. ⚠ The drain is visible in the source at the acquisition site and is
the mechanism consistent with the shape; the profile attributes the time to the acquisition as a
whole and does not separate the drain from the wait. Splitting those two is a further measurement,
not a conclusion available here.

WHAT THIS MEANS FOR THE PROJECT'S OWN NUMBERS: D58 and D59 took the READ path to x8.12 at 16
threads precisely by teaching reads to avoid this lock — the epoch mirror and `try_run_read` exist
for that. This measurement is the other half of the same structure: every writer, and every MERGE,
still takes it, AND drains the readers on the way in. So a merge does not merely serialise against
other merges, it stalls the read path that was freed. The read work was not wrong; it was half the
problem, and this is the half nobody had measured.

⚠ STILL A SHAPE, NOT A COMPARISON: "the write path serialises on one global lock and its
acquisition cost grows with concurrency" transfers to any engine built this way. The absolute
merges/sec is this machine on a shared box and transfers to nothing.

=== ⛔ CORRECTION TO THE SECTION ABOVE — I NAMED THE RIGHT LOCK AND THE WRONG MECHANISM ====
[HERE] read out of the banked sample's CALL TREE, which the aggregate-by-symbol view hid.

WHAT I WROTE: that the collapse comes from `catalog()` calling `drain_readers()` on every
acquisition, a scan whose cost grows with the number of live connections. I wrote that the same
day I wrote "that is a HYPOTHESIS READ OFF THE SOURCE, not a measurement" about the lock itself —
and then failed to apply the same standard one paragraph later. It is wrong, twice over:

  1. **This benchmark registers ZERO readers.** `grep -c register_reader examples/d67_*.rs` is 0.
     `drain_readers` copies an empty Vec and its spin loop never executes. There is nothing to
     drain, so draining cannot be the cost.
  2. **The drain is not in the blocked stacks at all.** Every blocked sample is
     `ServerContext::catalog + 60 -> Mutex::lock + 12 -> _pthread_mutex_firstfit_lock_wait`.
     Reading `catalog()` in source order: `self.catalog.lock()` comes FIRST, `drain_readers()`
     second. Offset +60 is the first acquisition. The threads are blocked on the CATALOG mutex,
     before the drain is ever reached.

SO THE LOCK IDENTIFICATION STANDS AND THE EXPLANATION DOES NOT. What actually produces a COLLAPSE
rather than the flat line a serialised section predicts:

  * **The critical section is the WHOLE STATEMENT.** `run(stmt, &mut cat, ...)` executes while
    holding the guard — parse, plan, execute, WAL. The lock is not held across a catalog lookup,
    it is held across the entire unit of work.
  * **The mutex blocks in the kernel.** Every handoff at 16 waiters is a `__psynch_mutexwait`
    round trip, and macOS's firstfit mutex is not FIFO-fair, so heavy contention convoys: the
    per-handoff cost rises with the number of waiters. Long critical section + kernel handoff +
    16 waiters is the textbook convoy shape, and a convoy collapses where pure serialisation
    would plateau.

⇒ **THE STRUCTURAL STATEMENT, and it is stronger than what I claimed before: ferrodb executes
EVERY WRITE STATEMENT while holding ONE GLOBAL MUTEX. Write concurrency is not poor, it is ONE by
construction.** A merge is six statements, so it takes and releases that lock six times, queueing
behind every other agent each time.

⚠ WHAT IS STILL NOT MEASURED, stated so the next reader does not inherit another guess: the
drain's `writer_active` SeqCst store and its `readers.lock()` are a shared-word write and a SECOND
global mutex on every acquisition. With readers registered — the real server — those would matter,
and D51 says a shared-word write on a hot path is exactly what does not scale. This benchmark
cannot see it because it has no readers. A version that registers reader slots is the run that
would.

=== PREMISE CHECK — IS THE HARNESS MEASURING WHAT THE SERVER DOES? =========================
[HERE] read from src/pgwire/extended.rs:325-362 at this commit. Checked because a benchmark that
calls an internal API directly can measure a path no client ever takes, and the whole D67 claim
rests on the harness being representative.

IT IS. The server's per-statement dispatch is:
    1. `ctx.read_catalog(catalog_cache)` — refresh the per-connection snapshot.
    2. `ctx.begin_read(read_slot)` then `try_run_read(..)` — the lock-free read path (D58/D59).
       `try_run_read` returns None for ANYTHING needing the catalog exclusively.
    3. On None: `let mut catalog = ctx.catalog(); run(stmt, &mut catalog, ..); drop(catalog);`

Step 3 is exactly what `examples/d67_merge_contention.rs::exec` does — `ctx.catalog()` then `run`
under the guard. Every WRITE and every MERGE takes step 3, because `try_run_read` answers None for
them. So the measured path is the shipped path, and the harness is not a shortcut.

The source says it plainly at extended.rs:355, and it is worth quoting because it shows this is a
KNOWN design point rather than an oversight:
    "**The catalog lock, held for exactly one statement.** See `pgwire::serve` for why this is the
     outermost lock and why holding it for longer would rebuild the sequential server this
     replaced."

⇒ The lock is already the result of making things BETTER: it replaced a wholly sequential server,
and holding it per-statement rather than per-connection was the improvement. D58/D59 then lifted
READS out of it entirely. What D67 measures is the part of that progression that was never
finished: writes still take it, one statement at a time, and a merge is six statements.
