WHICH FIRED
-----------
OUTCOME 1, and not marginally.

ARM A's acquisitions are EXACTLY LINEAR in T, with a constant per-fork cost at every thread
count in the sweep:

    A2 (one connection per fork):  24/8 = 96/32 = 384/128 = 1536/512 = 3.000 acquisitions/fork
    A1 (persistent connection):    33/8 = 132/32 = 528/128 = 2112/512 = 4.125 acquisitions/fork

Not "roughly one or more per fork, rising with T" -- three per fork, and the ratio column does
not move by a thousandth from T=1 to T=64. ARM B took ZERO at every T, in the same process,
against the same static, with a pgwire server built and listening beside it.

EVERY ACQUISITION IS ATTRIBUTED. This is the part that makes the result checkable rather than
merely plausible: the measured totals are not "consistent with" mediation, they are reproduced
exactly by counting the three sites the pre-registration named, with nothing left over.

  The three sites, confirmed in source (this tree, commit ed598e4):
    (i)   src/pgwire/extended.rs:283  `Statement::parse_one` -- one acquisition to infer
          parameter types and describe result columns. The SIMPLE query path reaches it too:
          `run_simple` -> `Statement::parse_batch` -> `parse_one`.
    (ii)  src/pgwire/mod.rs:257       inside `ServerContext::read_catalog`, refreshing a STALE
          per-connection snapshot. Fires once per connection here and no more -- `ctx.epoch`
          is the SQL catalog's epoch, which a branch fork does not move.
    (iii) src/pgwire/extended.rs:357  the exclusive execute arm, taken when `try_run_read`
          answers `None`. `BEGIN AGENT SESSION` and `ABANDON` are not reads, so it always does.

  A2 -- one connection, one statement each:   (i) + (ii) + (iii) = 3 per fork.
        T=1   8 conns x 3 =   24   measured   24
        T=4  32 conns x 3 =   96   measured   96
        T=16 128 conns x 3 =  384  measured  384
        T=64 512 conns x 3 = 1536  measured 1536

  A1 -- one connection per thread, 8 x (BEGIN + ABANDON) on it. Two statements per fork, each
        paying (i) + (iii); (ii) is paid ONCE for the connection because the fork does not move
        the SQL catalog epoch:  16 statements x 2 + 1 = 33 per connection.
        T=1   1 x 33 =   33   measured   33
        T=4   4 x 33 =  132   measured  132
        T=16 16 x 33 =  528   measured  528
        T=64 64 x 33 = 2112   measured 2112

  Residual in all eight cells: zero.

⚠ ONE CORRECTION TO THE HARNESS'S OWN PROSE, recorded here rather than left to ride.

  The harness prints "A0 is the per-connection/per-statement FLOOR: acquisitions a client pays
  for connecting and running a trivial statement". A0 measured 0 at every T, and the reason is
  NOT the shared read path, which is what the arm table's "the statement is a read, so it may
  take the shared read path instead" invites a reader to assume.

  `SELECT 1` never reaches the engine at all. `Statement::parse_one` tries
  `crate::pgwire::session::parse` FIRST and returns `Kind::Session` before the acquisition at
  extended.rs:283; `session::parse` routes a leading SELECT to `parse_probe`, and
  src/pgwire/session.rs:473-479 answers a bare integer literal as a liveness probe
  ("`SELECT 1` -- the oldest connection-liveness check there is"). `Statement::execute` then
  dispatches `Kind::Session(cmd)` to `run_session`, which does not touch the catalog either.

  So A0=0 is a true and useful control for the ONE thing E.6 needs it for -- it proves that
  opening 512 connections and completing a statement on each costs ZERO acquisitions, which is
  why the whole of A2 is attributable to the fork statement and its parse. It is NOT a floor
  for "a trivial statement that reaches the query engine": no such statement was run. A read
  that does reach the engine pays (i) at parse even when `try_run_read` then serves it without
  (iii). The conclusion is unaffected -- A2 - A0 = A2 either way -- but the label was wider
  than the measurement, and the measurement is the smaller of the two.


WHAT WAS ESTABLISHED FROM SOURCE BEFORE THE RUN (confirmed, not re-derived)
---------------------------------------------------------------------------
- src/pgwire/mod.rs, `serve`'s lock-ordering note: the catalog mutex is taken OUTERMOST, for the
  duration of a single statement, and "Nothing beneath it ever takes it back".
- `ServerContext::catalog()` is a real `Mutex::lock` (plus an unconditional reader drain).
- examples/fork_concurrency.rs constructs a `TableBranchCatalog` directly (:26, :32) and calls
  `cat.fork(BranchId::TRUNK, lease)` at :101. It holds no statement mutex and builds no
  `ServerContext`.
- The pgwire fork statement is `BEGIN AGENT SESSION AS '<agent>' RUN '<run>';`. It reaches
  `TableBranchCatalog::fork` through `AgentRuntime::begin_session_as`
  (src/agent_sql/runtime.rs, `self.branches.fork(parent, ...)`) -- the SAME `fork` arm B calls.
- src/agent_sql/dispatch.rs refuses a second `BEGIN AGENT SESSION` on a connection that already
  has one open, and `ABANDON` clears `session.agent`. That is why arm A1 alternates the two and
  arm A2 uses one connection per fork.
- Three distinct sites inside the pgwire path can take the counted lock for one statement:
  `Statement::parse_one` (describe/param-infer), `ServerContext::read_catalog` (refreshing a
  stale per-connection snapshot), and `Statement::execute`'s exclusive arm. The census counts
  acquisitions, not statements, so a ratio below 1 fork per acquisition is expected and is
  itself evidence of mediation, not against it.
  [CONFIRMED BY THE RUN. All three fire, and they are the whole of both A arms -- see the
   attribution above. The ratio came out at 0.333 for A2 and 0.242 for A1, both below 1.]


ARMS -- LAYER AND PRODUCTION LOCKS (the standing requirement E.6 promoted to a gate)
-------------------------------------------------------------------------------------
A1  layer: the shipped pgwire server, real TCP socket, one client connection per thread,
           forks issued as SQL (`BEGIN AGENT SESSION` / `ABANDON` per fork).
    production locks at this layer: ServerContext::catalog() OUTERMOST, one per statement
           -> AgentRuntime's Mutex<State> -> TableBranchCatalog's `logical`.
A2  layer: the same server, one connection per fork, a single `BEGIN AGENT SESSION` on each.
    production locks: identical to A1.
A0  layer: the same server, same client shape as A2, `SELECT 1;` in place of the fork.
    THE CONTROL. Establishes the per-connection/per-statement acquisition floor, so the fork
    statement's own contribution is A2 - A0 rather than the whole of A2.
    [SEE THE CORRECTION ABOVE for what this control does and does not establish.]
B   layer: `TableBranchCatalog` directly, as examples/fork_concurrency.rs does today.
    production locks at this layer: `logical` ONLY -- no statement mutex, because no shipped
    front-end reaches `fork` this way. The configuration that does is an embedded
    `AgentRuntime` caller, which is real and is what that harness actually models.

Arms A build the branch catalog with `default_for_database` (the pgserver.rs shape); arm B uses
`open_sidecar` (the fork_concurrency.rs shape). Same type, same `fork`. Stated rather than
smoothed over, and not the difference the result turns on: arm B cannot reach the counted lock
under either constructor.

NO LeaseThread runs in any arm. In production the lease scan takes this same outermost mutex
once per interval, so leaving it out makes every A count a LOWER BOUND on what production takes
-- the safe direction for the claim under test.

---------------------------------------------------------------------------------------------

   exits 1 otherwise.  [FIRED AND PASSED -- first line of the table output below.]
2. Arms A and B run in the SAME PROCESS against the SAME static. A's non-zero is the proof the
   instrument was live at the moment B read zero.  [A1+A2 = 4845 against B's 0.]
3. A pgwire server is built and listening while arm B runs. B reads zero because nothing
   connects to it, not because there is nothing to count.
4. The fork total is cross-checked against the branch identities the SERVER reported (arm A) and
   the distinct branch ids the catalog minted (arm B); a disagreement with the loop counter
   exits 1. No arm's headline number comes from this harness's own bookkeeping alone.
   [The server-side witness is the `branch_name` column of `session_started_columns()`
    (src/agent_sql/dispatch.rs), formatted `b_{id}` at src/agent_sql/runtime.rs:1541. It is a
    sound witness in this rig because ids are not recycled here: `AgentRuntime::with_storage`
    builds with `reaper: None`, and the reaper-less `seal` sets state to `Reaped` without

    recycled, the cross-check would have REFUSED rather than under-counted.]
