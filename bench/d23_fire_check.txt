ONE mutant survives, and it is a deliberate, reported negative — not an oversight.

WHY BREAK C IS KEPT ANYWAY. The scanner's per-leaf page latch is NOT load-bearing today, and
the signal is not vacuous: the live scanner completes 49-158 full concurrent scans per round
(214/319/290 at 32 threads in the independent run cited below) with live_scan_misses 0 and
live_scan_disorder 0. Two properties hold without it:
  - `frame.data` is assigned wholesale under the frame WRITE lock while readers take the READ
    lock, so a 4096-byte page read is already atomic; no scanner can see a half-written leaf.
  - a split writes the NEW leaf before writing the old one, and writing the old one is what
    publishes `next -> new_page_id`, so the chain never points at an unwritten page.
The latch is retained as defence in depth against that publish ordering being reversed. It is
documented as unproven at its definition in src/storage/range_scan.rs. Calling it load-bearing
would be false, and an earlier version of that doc comment did exactly that; it is retracted.

WHY BREAK B'S RESULT CHANGED. Against the test as it stood at de980e2, BREAK B did NOT fire, and
the code comment claiming it had been fire-checked was unearned. The full range scan ran AFTER
join(), so it was single-threaded. Adding a scanner that runs DURING the writes is what made the
parent latch's failure observable. The guard did not change; the instrument did.
