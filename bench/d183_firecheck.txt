WHY THIS FILE EXISTS
--------------------
D183 replaced four full-image rewrite sites on the reap path with appended tail records. The row
rests on those records reproducing what the rewrite produced — and this is a durability path, so a
record that is wrong is a page that never comes back or a page freed under a live reader. A green
test that has never been made to fail asserts nothing about that.

⛔ THE STRUCTURAL FINDING: A DOWNSTREAM RECORD MASKS THE ONE IN FRONT OF IT
----------------------------------------------------------------------------
`an_interior_reap_replayed_from_the_tail_is_byte_identical_to_a_full_rewrite` originally ran the
interior reap AND the drain, then compared once at the end. Mutant M1 — the parked record silently
dropping its last entry — PASSED that test.

The reason is structural, not a slip: the drain's record carries the pending log, so it restates
whatever `TAIL_PAGES_PARKED` got wrong. A downstream record that re-states the same state masks
every mutant of the one in front of it, exactly as a redundant downstream check does. The test now
compares after EACH record, so the parked record is examined while it is still the last word on
the log.

⛔ THE SECOND STRUCTURAL FINDING: AN ALWAYS-CORRECT FALLBACK HIDES THE THING IT BACKS UP
------------------------------------------------------------------------------------------
`put_pending` writes the O(released) difference record only while `PersistState::drain_mark` proves
the durable log is the one `take_pending` handed out, and the O(whole log) absolute record
otherwise. Every drain in the suite satisfies the proof — so a weakened proof that said "usable"
always would have passed every test in the file, and the fallback would have been untested code
that still compiles. Two things were added: `a_drain_that_cannot_prove_the_log_falls_back_to_the_
absolute_record`, which invalidates the proof two different ways and requires the fallback to be
exact; and a `tail_kinds` assertion at each stage of the restore test, because `persist_counters`
says how many records were appended and cannot say WHICH.

WHAT M3 AND M4 SAY ABOUT THE REST OF THE SUITE
-----------------------------------------------
Both are recycled-list defects, and under both the OTHER arena tests passed. The durability of the
per-extent recycled list across a reap had no test before this row — `retire_arenas_by_rule`'s own
comment says losing it leaks the extent permanently, and nothing was checking.

NOT CLAIMED HERE
----------------
The order-independence argument — that a `TAIL_EXTENT_FREED` for the same arena may land on either
side of these records because they skip arenas absent from `extents`, that the `(page, arena)`
dedupe makes the parked record safe to replay behind a drain record, and that an overlapping drain
poisons the mark — is NOT fire-checked. It needs two threads racing a reap against an extent free,
which this harness cannot arrange. It is argued in the code at each replay arm and at
`take_pending`, and it is the weakest part of this row's evidence.
