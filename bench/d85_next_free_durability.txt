6. FINDING: THE RETIRE-SIDE PROBE IS AN UNTESTED GUARD (not dead code)
------------------------------------------------------------------------
`retire_arenas_by_rule`'s `self.resolve_fill(arena)` (arena.rs, D85 comment above it) can be
deleted with no test anywhere failing.

MECHANISM -- REASONED FROM SOURCE, NOT MEASURED. Without the probe, a restored extent's
`allocated_pages` is `(0..understated next_free)` minus `recycled`, so the loop parks nothing
and releases nothing. SAFETY STILL HOLDS: the `extent_is_empty` refusal plus the
collectable-side probe keep the extent from being freed. What is lost is RECLAMATION --
`recycled` never grows, the collectable-side probe later raises `next_free` to the truth, so
`recycled >= next_free` stays false and the extent is never collected. That is a SPACE LEAK on
the crash-plus-live-children path, not data loss, which is exactly why every safety-direction
test passes and nothing fails.

The missing test is the RECLAMATION direction on that path: crash-restore, reap a parent that
HAS a live child, retire the child, then assert the extent is eventually collected. The
existing D85 end-to-end test constructs that shape but asserts only the safety direction
(`arena_owner(arena).is_some()`).

⚠ This row already hit `two guards is one you cannot test` once and closed it for
`extent_is_empty`'s refusal by giving that guard its own test rather than deleting it. Same
remedy applies here. NOT FIXED IN THIS PASS -- the brief was prove-or-disprove.


7. CORRECTION TO THE ROW'S STATED LIMIT: the "2 of 3" is misattributed
------------------------------------------------------------------------
The row says: "the probe recovers only pages that REACHED DISK (2 of 3 in the test); a page
still in the buffer pool at crash time was never durable, so nothing is lost by missing it."

The 2-of-3 is REAL (`D85 probe: recovered 2 page(s) (wanted 3)`, measured with --nocapture,
since cargo swallows stdout for PASSING tests -- which is why this number was not visible in
the earlier arms). BUT ITS STATED CAUSE IS WRONG. Arm 7, a diagnostic that prints `next_free`
and `recycled` separately:

  D85 arm7: image next_free=1 recycled=[8]
  D85 arm7: wrote after the image [8, 9, 10] (of which REUSED a recycled id: [8])
  D85 arm7: restored next_free=1 -> after probe 3
  D85 arm7: recycled after restore=[8]  allocated_pages=[9, 10]

The probe recovered the FULL truth: next_free 1 -> 3, all three pages. Nothing failed to reach
disk. The page that "went missing" is page 8, hidden because `allocated_pages` SUBTRACTS the
restored `recycled` list, and page 8 was recycled before the image and REUSED after it
(`alloc_in_arena` pops `recycled` before bumping, arena.rs:1395).

The row's general statement about the probe's disk limit remains true as a property of
`resolve_fill` -- it stops at the first unreadable page. It is simply not what this measurement
shows, and the "2 of 3" should not be cited as its evidence.

IS THE STALE `recycled` ENTRY A SECOND HAZARD? NO -- checked and killed. Page 8 is listed free
while holding live post-image data, but it is never handed out: the only consumer of
`has_recycled` is `arena_for`'s fast path (arena.rs:1680), gated on `st.current.get(&branch)`,
and `load_state` CLEARS `current` (:1184). A restored extent is never re-entered for
allocation. Worth recording because load_state's own comment justifies keeping `recycled` as
"those pages were durably recorded as free *before* the checkpoint, so handing them out again
is correct" -- which is weaker than the guarantee the code actually rests on. It rests on
`current.clear()`.

---------------------------------------------------

once per extent per restore, asked only for DEAD owners (`extent_is_collectable` probes after

production restore paths funnel through `load_state`: arena.rs:1285 `restore`, arena.rs:1336
`reopen_from_checkpoint`, consensus/snapshot.rs:1541 `install`. No gap.
