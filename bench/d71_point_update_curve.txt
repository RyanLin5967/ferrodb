D71 — THE WALL IS THE AGENT STAGING PATH, NOT THE MERGE AND NOT THE ENGINE.

[HERE] `examples/d71_point_update_curve.rs`, built at 991d6e0 (+DIRTY at run time — the instrument
edits were uncommitted; they are committed at 2ddeee1 and the code is identical). Load 99 -> 23
across the two arms, so absolutes are inflated and unstable; the SHAPE is the result.

PRE-REGISTERED before the run, three outcomes, written into the harness:
  * PLAIN flat, STAGED linear -> the wall is the agent staging path.
  * BOTH linear               -> the planner is not using the primary index; a general engine bug.
  * BOTH flat                 -> the slope is neither, and d69_fsync_counted.txt is wrong.

=== OUTCOME 1 CONFIRMED ===============================================================

**The general engine path is O(log N). The branch-per-agent staging path is O(table) — per write.**

This is the entire slope that D68 attributed to the merge, that D69 tried to fix in the merge, and
that D69-REOPEN attributed to fsync scaling. None of those were it. The merge is O(delta)
(`bench/d69_fsync_counted.txt`: WAL bytes = 229 + 206 x delta, exact over a 32x range, one fsync).
The plain engine is O(log N). The linear term lives in exactly one place and it is the path that
only exists because of branching.

⚠ **NOTE THE ABSOLUTES BEFORE READING THIS AS A DISASTER.** STAGED is 20x FASTER than PLAIN at
1,000 rows (0.185 ms vs 4.032) because it does not fsync. It is a linear curve starting far below
a flat one, so the crossover is what matters, not the slope alone: extrapolating the fitted rates
(~0.149 us/row staged, ~5.4 ms flat plain) they cross near ~36,000 rows. Below that, staging is
still the faster path. ⚠ That crossover is ARITHMETIC ON TWO FITS, not a measurement — the largest
table measured here is 16,000 — and the fsync floor in PLAIN is load-dependent on a box at load 99,
which moves the crossover directly. It is a pointer to the next measurement, not a result.

⇒ **THE ROW THIS OPENS: make a staged write a DESCENT.** The objective is 10^6 branches on real
tables; a per-write cost linear in the table is the wall that reaches first, and unlike the last
three rows it is now located by a control arm rather than inferred from a profile.

=== WHAT THIS CANNOT SAY ==============================================================
  * INTEGER keys only, as every curve here.
  * It does not name the mechanism inside the staging path — only that the path is linear and the
    engine path beside it is not. Naming it is the next step and must be read off the source, not
    inferred from this curve. Two rows have already been lost to inferring a mechanism from a shape.
  * The crossover is arithmetic on two fits, at one load, at one delta. It is not measured.

=== A SECOND WALL I PROPOSED AND THEN KILLED BY MEASURING IT ==========================

Profiling the staged arm at N=4000 updates showed a median of 4.299 ms against 2.385 ms at N=60,
and the profile's heaviest frames were `RawVecInner::finish_grow` and `do_reserve_and_handle` —
vector GROWTH, not I/O and not scan logic. The obvious reading was a second, nastier wall: a
branch gets slower the more it has already written, because the staged workspace is walked per
write (`runtime.rs:1423`, the `None` arm ranges the whole table prefix of the overlay). For an
agent that writes a lot into one branch that would be quadratic in its own session.

**Measured instead of banked. Fixed 4000-row table, varying the number of updates IN the session:**

  updates in session (N)    median ms per update
                      50                   0.708
                     100                   0.695
                     200                   0.717
                     400                   0.765
                     800                   0.762
                    1600                   0.790
                    3200                   1.027

⛔ **64x the session size costs 1.45x per update. THE HYPOTHESIS IS DEAD.** The overlay walk is
sublinear in practice — consistent with a BTreeMap range plus allocator pressure, not with a walk
proportional to staged rows. There is no session-size wall and no quadratic term.

⇒ It also explains the profiling run's higher median without a new mechanism: that run was at
16,000 rows, 4x the 4,000 used here, and 4.299 / 1.027 ~ 4.2. **That is the table-size term
already named above, not a second one.** The two axes are now separated: staged write cost is
LINEAR in TABLE SIZE and essentially FLAT in SESSION SIZE.

⚠ And the `finish_grow` frames stay UNEXPLAINED rather than being attached to the dead hypothesis.
They are consistent with open row D26 (`CowTree::range_scan` materialises the whole result and the
caller collects it again, Theta(table)) — which is a TABLE-size mechanism and therefore the right
shape — but consistent-with is not measured, and this file has already cost three rows of
mechanisms inferred from shapes. D26 is the candidate to test, not the answer to record.
