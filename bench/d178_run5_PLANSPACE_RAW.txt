date   : 2026-09-23T13:18:55Z
harness: examples/d178_planspace_diff.rs, one binary, built twice from the same source:
         once with the H1 guard, once with only the guard's four lines reverted.
         Worktree /Users/idide/wt/ferrodb-d178-planspace at a9fd980.

WHY THIS RUN EXISTS. The H1 fix narrows what build_index_scan may PROPOSE, and that is
SELECT's planner, not just DML's. 'It only removes plans that could not run' was an
ARGUMENT I made from the code's structure. This measures it instead, and the measurement
is NOT what the argument predicted.

RESULT: 7 of 104 corpus rows differ. On EVERY row where both trees answer, the row set is
identical -- same count and same checksum. No answer changed anywhere. But the 7 rows are
of TWO kinds, not one:

  (1) SIX rows, fixture n=800 ANALYZE=true: unguarded ERRORS, guarded answers correctly.
      The index candidate wins the cost comparison and then cannot be lowered.

  (2) ONE row, fixture n=800 ANALYZE=FALSE: BOTH trees answer, and the PLAN differs.
        v > 7980 AND id = 799   unguarded -> Sequential scan (rows=1000 cost=23.00)
        v > 7980 AND id = 799   guarded   -> Index scan on col 0 ([799,799]) cost=13.00
      Both return 1 row, sum=799. The guarded plan is strictly better.

⭐ THE MECHANISM BEHIND (2), AND IT IS THE MORE INTERESTING HALF OF THE H1 DEFECT.
  build_index_scan picks the FIRST conjunct carrying an index. An unlowerable conjunct
  therefore CONSUMED THE CHOICE, and a later usable index was never considered. Whether
  that ended in an error or merely a worse plan depended on the COST COMPARISON:
    - with statistics, the index candidate WINS the comparison, is returned, and then
      lower() refuses it            => a hard ERROR  (kind 1)
    - without statistics, it LOSES the comparison, so build_index_scan returns the seq
      plan and nothing errors       => a SILENTLY WORSE PLAN  (kind 2)
  So the same defect has two faces depending on whether anyone ran ANALYZE, and only one
  of them is visible as a failure.

⭐ IT WAS ALSO ORDER-DEPENDENT, which the corpus caught by carrying both spellings:
        v > 7980 AND id = 799   unguarded -> Sequential scan
        id = 799 AND v > 7980   unguarded -> Index scan on col 0
  The same predicate, the same answer, a different plan, decided by the order the user
  happened to type the conjuncts in. The guard removes that.

⇒ NET: of 104 rows, 97 identical, 6 ERROR -> correct answer, 1 worse plan -> better plan.
  Nothing got worse and no answer moved. But 'the guard only removes unexecutable plans'
  is FALSE as stated: it also stops an unusable conjunct from shadowing a usable one.
