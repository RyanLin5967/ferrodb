THE QUESTION
------------
D50 measured ferrodb's server flat: 15 extra threads buy nothing, because
src/execution/executor.rs:60 is

    pub fn run(stmt: Stmt, catalog: &mut Catalog, ...) -> Result<Outcome, FerroError>

and src/pgwire/mod.rs:64 holds one Mutex<Catalog>, taken outermost for a whole statement
(mod.rs:100 says so in its own lock-ordering note). The question that decides whether that is
fixable at all: DOES A READ ACTUALLY NEED THE CATALOG TO BE MUTABLE?

"&mut" is a TYPE decision, and a type decision has a better instrument than reading the code.

=> The serialization is NOT a property of what a read does. It is ONE type signature,

WHAT THIS DOES NOT SAY
----------------------
It does not say the fix is cheap, and it does NOT say the standard answer (swap the Mutex for
an RwLock) works. D49 measured, on turso, that a per-statement SHARED lock acquisition is
itself an entire scaling wall: x0.308 total at 16 threads, with the readers doing LESS total
work than one. A read path that takes &Catalog is the PREREQUISITE, not the mechanism.

A HARNESS NOTE, BECAUSE IT NEARLY COST THE RESULT
-------------------------------------------------
The first capture of this probe used `cargo check 2>&1 > file`, which sends stderr to the OLD
stdout (the terminal) and only stdout to the file. `grep -c '^error'` on the resulting empty
log printed 0 -- a clean-looking zero produced by a discarded stream, which reads exactly like
"nothing broke". Correct order is `> file 2>&1`.
