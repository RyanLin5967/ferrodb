================================================================================
1. THE DEFECT, AND WHAT THE FIX IS
================================================================================

`TableBranchCatalog::upsert` was:

    match self.tree.delete(&key) { Ok(()) | Err(KeyNotFound) => {}, Err(e) => return Err(e) }
    self.tree.insert(key, value)

`BPlusTreeManager::delete` takes the leaf's write latch and **drops it on
return**; `insert` re-acquires it. Nothing is held across the two, so between
them the key does not exist in the tree. `write_record` routes the branch RECORD
key straight through that pair, reached from `set_state`, `set_root`,
`renew_lease`, `reparent`, `restrict_envelope` and `put` — `set_root` and
`renew_lease` being ordinary hot-path writes. Every reader of a record (`core`,
`get_raw`, `has_live_children`, `max_live_child`, `live_child_in_epoch_range`)
takes no lock at all: `logical` is writers-only.

The fix is `BPlusTreeManager::upsert`, the replace primitive the tree did not
have — which is precisely why the catalog open-coded the pair. The removal and
the addition are applied to ONE in-memory leaf image, so the single `write_page`
that publishes the new value is the same one that drops the old. The
does-not-fit case splits that already-mutated image, and the existing split
ordering (new right sibling written first, halved leaf second, because writing
the halved leaf is what publishes `next`) keeps the key reachable throughout.

3. WHAT I ADDED — (a) AN ENTRY LARGER THAN A PAGE NOW REFUSES INSTEAD OF PANICKING
================================================================================

Commit 7be7627.

`BPlusTreeLeafPage::split` takes `mid = len / 2`. On a leaf holding ONE entry
that is 0, so `split_off(0)` moves everything to the new page and leaves this
leaf EMPTY — and `serialize` on the oversized half then indexes past `PAGE_SIZE`.

MEASURED, before the guard, on the test that now covers it:

    thread '...an_entry_larger_than_a_page_is_refused_rather_than_split_into_an_empty_leaf'
    panicked at src/storage/index_page.rs:117:
    range end index 4143 out of range for slice of length 4096
    (27 header + 12 key + 4104 value)

**D126 is why this is written down now.** `insert` could only reach the case on
an EMPTY leaf. `Replace` reaches it on a POPULATED one: a replacement value can
grow a one-entry leaf past the page without ever making it two entries, which is
a shape no `insert` can produce. The guard refuses by name, before anything is
written, and it is strictly stricter than what it replaces — it refuses nothing
that previously succeeded, because what it catches previously panicked.

Fire-checked from both directions (upsert-grows and insert-into-empty), with a
negative control in the same body: a 2000-byte value is still accepted, and 40
ordinary inserts still split and are all still findable afterwards.

Not reachable from the branch catalog — a serialized core record is tens of
bytes — but `BPlusTreeManager` also backs every user table's primary index.

5. SCOPE — WHAT D126 DOES NOT DO. STATED SO THE GUARANTEE IS NOT OVER-READ.
================================================================================

**D126 makes one KEY's value change atomic. It does NOT make `write_record`
atomic.** The state and deadline index keys are not rewritten in place, they
MOVE: `remove_if_present(keys::state(old_state, id))` first, then
`upsert(keys::state(new_state, id))` several lines later. Between those two a
branch is in NEITHER state span and NEITHER deadline span, and `live_count`,
`in_state` and `expired_before` scan exactly those spans without the `logical`
lock. No per-key primitive can close that — they are different keys, in general
on different pages.

The direction it fails in is benign for the reaper: `expired_before` missing an
entry reads as "not expired yet", and `reap_if_still_expired` re-reads the record
anyway. `live_count` can undercount by one for the length of a rewrite. That is
why this is noted rather than treated as the same defect — but it IS a real
multi-key window and it is a separate row, not something D126 closed.

Also unchanged: D124's guards, D127's swallow, and the fact that none of this is
reachable in production today because reader and writer are both inside the
per-statement mutex. W4 removes that mutex. D126 is now in front of it.

6. WHAT I ADDED — (c) THE THREE OPEN-CODED REWRITES STILL LEFT IN src/
================================================================================

Commits 5388fda and a3114d0. The primitive was added for the branch catalog,
and the identical pair was left open-coded on a user table's PRIMARY INDEX in
three places:

  src/execution/update.rs   if new_rid != rid { primary_index.delete(&pk)?;
                                                primary_index.insert(pk, new_rid)?; }
  src/execution/insert.rs   primary_index.delete(&vals[0])?;
                            ... heap.insert(tuple)? ...
                            primary_index.insert(vals[0], rid)?;
  src/catalog/alter.rs      if primary.search(&k)? == Some(rid) {
                                primary.delete(&k)?; primary.insert(k, new_rid)?; }

The second is the worst: a whole heap insert sits inside the window. All three
are now one `upsert`.

`update.rs` also loses an error path that could only fire AFTER the heap was
already updated — `delete` returns `KeyNotFound` for a missing entry and
propagating it aborted the statement with the index left disagreeing with the
heap; `upsert` repairs the entry instead.

`alter.rs` keeps its `search(&k) == Some(rid)` guard, and that is load-bearing:
`upsert` INSERTS a key that is absent, which is exactly what a rewrite must not
do — a deleted row keeps its heap tombstone AND its index entry. The guard
decides whether to write; `upsert` only decides how.

That is every open-coded delete-then-insert on a `BPlusTreeManager` in `src/`,
enumerated from a grep for `.delete(` rather than from memory. What remains is
`TableBranchCatalog::remove_if_present` (a genuine removal) and the CoW tree's
own root-returning `delete(root, branch, epoch, key)`, which is a different
structure with a different API and not this defect.

Probed with the REAL types rather than assuming the `Vec<u8>` result carries
over (`Value`/`RecordId` serialize differently and land differently in a leaf):

    D126 primary index CONTROL  (delete+insert): misses=34675 reads=65026  <- FIRES
    D126 primary index TREATMENT (upsert)      : misses=0     reads=30354

plus a duplicate count walked over the whole leaf chain (1 entry) and the last
value readable back.

⚠ SCOPED IN THE TEST'S OWN DOC: this probes the INDEX, not a concurrent
`UPDATE`. Two statements cannot reach the executor at once today — the pgwire
server serialises whole statements behind `ServerContext::catalog()`, the same
exclusion that keeps the catalog's window latent — so a SQL-layer probe would
need that lock bypassed, which is a harness of its own. The window is in the
index and so is the fix.

================================================================================

Read rather than assumed, because a fresh context's job is to attack the work and
not to restate it:

  - `apply_to_leaf`'s `let _ = leaf.remove_entry(&key)` discards a Result. Checked
    `index_page.rs:416`: `remove_entry` has exactly one failure arm, `binary_search`
    missing -> `KeyNotFound`. The comment's claim that "there is nothing else it
    can fail on" is TRUE.
  - **The sharpest hazard, and it is not one.** If `latch_leaf_for_write` could
    return a leaf that does not hold the key — a concurrent split having moved it
    right — then Replace would remove nothing and insert a second copy, which is
    the duplicate-key corruption the primitive exists to avoid. It cannot:
    `index.rs:474-489` keeps the PARENT's read latch across dropping the leaf read
    latch and taking the leaf write latch, and re-checks the root-as-leaf case.
    **`insert` already rests on that exact invariant** — without it an insert would
    land in the wrong leaf and break key order — so Replace inherits it and adds
    no new requirement.
  - The open-coded-pair sweep was re-run independently from `grep -rn "\.delete("
    src/ --include='*.rs'` rather than from section 6's list. It agrees: the only
    `.delete(` left on a `BPlusTreeManager` are `remove_if_present` (a genuine
    removal) and the probe's own control arm at `table_catalog.rs:1492`. Everything
    else is `cow/`'s root-returning `delete(root, branch, epoch, key)`, a different
    structure, or heap/WAL slot deletes. **No fourth site.**
