log bytes quadruple when N doubles (x3.87, x3.93, x3.97, x3.98) and so does reopen time.
That is O(N^2), and the mechanism is not inferred: `LogBranchCatalog::fork` clones the parent
record and appends it WHOLE, and `live_children: Vec<Epoch>` lives INSIDE that record - so the
bytes written per fork grow with the number of children the parent already has.

Extrapolated from the measured curve: 50k branches ~10GB of branch metadata, 1M ~4TB, with a
reopen in hours. Not a tuning problem.

Per-fork LATENCY is flat (~4-5ms, fsync-bound) and total time is LINEAR, so this is invisible to
any benchmark that measures fork latency. examples/branch_scaling_bench.rs cannot see it at all:
it uses LogBranchCatalog::in_memory, which never writes. Its x8.90 fork degradation at 50k is the
in-memory clone cost only - the optimistic half of the picture.
