SUBJECT: the `MERGE;` statement, reaching AgentRuntime::evaluate_merge (runtime.rs:4024).
QUESTION: is the production merge already proportional to the diff? If it is, cow::merge3's

INSTRUMENT: a PageStore decorator counting read_page, bracketing the MERGE statement AND NOTHING
ELSE. Integers, not durations — and the phase split is not optional here. D68/D69 spent three rows
misreading this exact curve because one wall clock wrapped `BEGIN AGENT SESSION` + N `UPDATE`s +
`MERGE` and the total was reported as "merge latency"; the linear term was in the UPDATEs
(bench/d69_fsync_counted.txt).

WHY A NEW INSTRUMENT AT ALL: the existing one (d69_fsync_counted) counts WAL bytes and fsyncs.
Those are WRITE-side and structurally blind to a read — a full table scan reads everything and
writes nothing. This closes the read side of the branch engine.

PRE-REGISTERED, written before the first run:
  * FLAT merge reads  -> merge already O(delta); merge3 buys nothing; say so and stop.
  * RISING            -> a table-size term exists and merge3 is the mechanism for it.
  * A rise in the WRITES column is NOT a result for this row — that is the separate wall D69
    already named, and it has its own column so it cannot be mistaken for the merge's cost.
  * ⚠ A ZERO IS NOT A PASS. A merge that did not happen reads no pages, and a dead counter reads
    the same as a perfect one. The run REFUSES (exit 2) unless the counter is first forced to
    fire, and refuses if no merge applied or fewer than two sizes were reached.

⚠ BLIND SPOT, STATED IN THE INSTRUMENT ITSELF: this counts branch-engine pages (ArenaPageStore,
what PagedRows and cow::merge3 use). It does NOT see the ordinary-table side — BufferPoolManager
exposes no public fetch counter in this build. A column for it was drafted and DELETED rather than
shipped returning a constant zero, because a counter that cannot fire is worse than no counter:
its zero reads as evidence. The `writes reads` column is the partial control (same planner, same
buffer pool). So this proves the CoW tree is untouched by a merge; it does not measure the heap.

The pre-registered branch was FLAT vs RISING. The answer was neither: it is ABSENT. A MERGE issues
zero branch-engine page reads at every size, and the fire-check (110 and 128 reads on put_row /

MECHANISM, read from source and agreeing with the measurement:
  * `self.rows()` — the only door to PagedRows — has exactly FIVE call sites in runtime.rs
    (put_row :1286, get_row :1303, delete_row :1314, scan_rows :1334, page_changeset :1842).
    `evaluate_merge` is not one of them.
  * The merge enumerates its delta from `snapshot.rows`, the workspace's own touched-rows map,
    and does one PK point lookup per touched row, which the planner turns into an IndexScan
    descent (has_index true for col==0, optimizer.rs:148; Equal -> point range, plan.rs:165).
  * So the real merge is O(delta · log N) and never walks a tree to find its delta.

⇒ merge3 skips identical subtrees. That is an advantage over a merge that would otherwise WALK the
  tree, and none at all over one that never walks it. Wiring it here is a STORAGE MIGRATION —
  moving base tables into the CoW tree — not a merge change. runtime.rs:1786 says so itself, in
  the future tense: "when base tables live in the tree as well, the fork root will hold real rows".

⚠ WHAT THIS IS NOT: not a comparison against Dolt or Postgres, and not a measurement of the heap
  side. It is a shape, in this engine, on the branch-engine store.
