THE PREMISE -- STATED WRONG FIRST, THEN MEASURED

  The row was opened on this claim: "a record key is never removed anywhere in `src/`, so a
  missing record can only mean 'not published yet'." I confirmed the grep and built the first
  version of this change on it, writing "impossible" into eight comments.

  THE CLAIM IS HALF TRUE, AND THE FALSE HALF IS THE ONE THAT MATTERS.

  DURABLY it holds. Nothing ever leaves a record deleted: retirement is a state flip to
  `Reaped`, the id-reuse path overwrites the recycled slot, and `keys::record` is only ever
  inserted, searched and upserted -- the same fact `write_record_new`'s "provably new"
  argument already rests on. `LogBranchCatalog::state.records` and `MemCatalog::records` have
  no `remove` either.

  TRANSIENTLY it fails, and the window is on the hot path. `BPlusTreeManager` has no replace
  primitive -- `TableBranchCatalog::upsert`'s own comment says so and is why the catalog
  open-codes delete-then-insert -- and `write_record` routes the RECORD key straight through
  `upsert`. `BPlusTreeManager::delete` takes the leaf write latch, writes the page and
  RETURNS, dropping the latch; `insert` then re-acquires it. Between those two calls the key
  DOES NOT EXIST. `write_record` is reached from `set_state`, `set_root`, `renew_lease`,
  `reparent`, `restrict_envelope` and `put` -- `set_root` and `renew_lease` are ordinary
  statement-path writes. Every reader this row touches is LOCKLESS: `logical` is a
  writers-only mutex and `core()` takes nothing.

  So a reader can see "no record" for a perfectly healthy, live branch, and the four sites
  below were FREEING ITS PAGES on that reading.

  Verified in source, not accepted on assertion: `src/storage/index.rs` `BPlusTreeManager::
  delete` (`let (page_id, _latch) = self.latch_leaf_for_write(key)?` -- scoped to the call),
  `src/branch/table_catalog.rs` `upsert` and `write_record`, and the absence of any lock in
  `core` / `child_liveness` / `live_child_at` / `has_live_children`.

  This makes the defect WORSE than the row was opened on, and the fix more valuable: it is a
  reachable data-loss race, not an impossible-state hardening. It does not change a line of
  the fix. It changes the cost profile: under W4 the guard fires a refusal on a healthy
  database rather than silently freeing, which is the right trade and not the end state.
  SCALE-DESIGN D126 -- give the tree a real replace so `upsert` is atomic -- closes the window
  and makes the original premise true. D126 is deliberately NOT in this row: it is a
  storage-layer change and mixing it in would make this guard unreviewable.


FOUR SITES, NOT TWO. All four resolved an unreadable record in the destructive direction.

  1. table_catalog::child_liveness       None => ChildLiveness::Gone
     `has_live_children` then skipped `Gone` entirely (`=> {}`), so the entry pinned nothing
     and the parent became reclaimable.

  2. table_catalog::live_child_at        `_ => Ok(None)`
     The catch-all whose own comment admitted it lumped "reaped with nothing under it"
     (legitimate) together with "gone entirely", answering the destructive way for both.

  3. reaper::drain_pending_seeded        `Err(_) => false` -> release_page
  4. arena::free_page                    `get_raw(owner).is_ok() && ...` -> release_page
     The same defect on the PAGE path, and both stated the false premise in their own
     comments ("no record at all: nothing can be forked off it"; "an owner with no record at
     all pins nothing"). Sites 3 and 4 are the CONSUMER and the PRODUCER of the same
     pending-free entry.

  Site 4 was not in the brief. It was found by enumerating the other producers of
  `PendingFree` while checking site 3's reachability. `cow/store.rs`'s `free_page` has the
  same shape but is NOT this defect: it reads its own in-memory `live_children_of`, never a
  catalog record.


REACHABILITY, stated honestly

  Not reachable in production TODAY. `reap_expired` runs inside `with_lock`
  (`lease_thread.rs`), which in production is the pgwire per-statement mutex that every
  `fork`, `set_root` and `renew_lease` also takes, so reader and writer are mutually
  excluded. W4 exists to remove that lock. The defect must be gone BEFORE W4 lands, not
  after. `tests/d15_concurrent_fork_and_reap.rs` bypasses `RuntimeLock`, which is where it is
  reachable at all today.

  An extent's owner is published BY CONSTRUCTION, which bounds what sites 3 and 4 can see:
  `alloc_arena` is the only writer of the extent map and it ends in `catalog.add_arena`,
  which both catalogs refuse for a branch with no record (`TableBranchCatalog::add_arena` and
  `LogBranchCatalog::add_arena`, each `ok_or(BranchError::NotFound(branch))` before writing
  anything). So those two sites were never seeing "an owner that never existed" -- only a
  transient miss or a genuine read failure, and they freed on both.


THE FIX

  Entry point first. `attach_child` refuses a `child_id` with no record
  (`BranchError::NotFound`), so the PERMANENT form cannot be created through the only API
  that could create it. It does not and cannot remove the transient form, which is why the
  resolvers still have to refuse. One extra point lookup; `migrate_from` is the only
  production caller (D63 deleted `collapse`) and it already writes every record before it
  attaches anything, precisely so this resolution can succeed.

  Both resolvers return `BranchError::Corrupt` naming the entry (parent, fork epoch, child
  id) instead of resolving it. `ChildLiveness::Gone` is DELETED rather than left
  unconstructed -- prepush builds with `-D dead_code`, and an unconstructed variant only
  invites the next reader to resolve into it again. A new `keys::child_parent_from_key`
  exists so the error can name the entry from the key alone.

  `live_child_at`'s `Some(_)` arm is split out of the catch-all and is UNCHANGED in
  behaviour: reaped with nothing below stays "not a live child", which is what `reap`'s crash
  window leaves.

  Sites 3 and 4 propagate the error. One thing came with that and is not cosmetic:
  `drain_pending_seeded` calls `take_pending()`, which has ALREADY emptied the durable log by
  the time a refusal happens, so returning with entries still in hand would DROP them -- the
  pages neither released nor ever revisited, turning a refusal into a permanent reservation.
  Everything undecided now goes back through `put_pending` before the refusal. The
  pre-existing `?` on `live_child_in_epoch_range` had the same hole and now goes through the
  same path. This is D83's reasoning for the `touched` set, applied to the `entries` list.

  Because the miss is usually transient, every refusal is RETRYABLE by construction: the
  CHILD entry stays, the pending entry goes back in the log, and the next sweep succeeds.


WHERE THE ERRORS GO, checked rather than assumed

  The reaper's two `has_live_children` callers -- the cascade loop in `detach_from_parent` and
  the fast-path guard in `reap` -- both use `?`, so a refusal aborts that reap and frees
  nothing. `TableBranchCatalog::release_id` swallows errors into `reusable = false`, so a
  refusal leaks an id slot rather than recycling one whose subtree cannot be resolved; that is
  the trade that method's own comment already documents.

  `reap_if_still_expired` converts any `FerroError::Branch(_)` from `reap` into "did not
  reap". That now swallows a D124 refusal too. LEFT ALONE DELIBERATELY: the outcome is safe
  (nothing is freed, the next sweep asks again), and propagating it would turn a benign
  already-reaped race into a failed sweep for a whole pre-existing class of errors -- a change
  well outside this row.

HOW THE STATE IS CONSTRUCTED

  Branch path: the CHILD entry is written straight into the tree with `upsert`, past
  `attach_child`, naming branch 4242, which was never forked.

  Page path: NOT by corrupting a catalog -- the arm catches an `Err`, not an absence, so an
  absence would not reach it. A decorator (`HidesOneRecord`) makes `get_raw` return `NotFound`
  for exactly ONE id and delegates every other method untouched, which is the same input the
  transient `upsert` window produces. Run over BOTH catalogs, because sites 3 and 4 live in
  code every catalog shares.
