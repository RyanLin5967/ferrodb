     FALSE for the read path, which is the path that matters for BranchBench. src/branch/mod.rs:9
     states the invariant and src/agent_sql/persistent_map.rs:33 restates it: a child's root IS
     its parent's root at fork, so a read is a descent of the child's own tree and its cost does

  3. "Every merge needs a common ancestor."
     FALSE as stated. ferrodb computes no LCA at all, and does not need one, because every merge
     targets the DIRECT PARENT: src/agent_sql/runtime.rs:2403 and :2692 both read
     `parent_id.unwrap_or(BranchId::TRUNK)`. src/tel/engine.rs:336 takes the LCA as `_lca` and

So the gap is not a slow ancestry query. THE GAP IS A MISSING CAPABILITY: because no LCA exists,
two SIBLING branches cannot be merged with each other at all. SIMULATE forks K candidates off one
base and can only admit them one at a time into the shared parent, each re-scored against a base
the previous admission moved. Merging candidate 3 into candidate 7 directly needs their fork
point. That is what this row makes possible.

## WHAT WAS BUILT

src/branch/version_graph.rs — binary lifting (jump pointers), Myers 1983. Each node holds its
depth and jump[k] = its 2^k-th ancestor. A child's table is built from its parent's alone.

  depth O(1) | level_ancestor O(log d) | is_ancestor O(log d) | lca O(log d) | insert O(log d)

Rejected, with reasons, in the module header: nested sets / interval labelling (Dietz 1982,
Celko, Django-MPTT) — O(n) renumbering per insert, disqualified because branches are created
live; ORDPATH / SQL Server hierarchyid (Li & Moon 2001) — strongest rival, O(1) ancestor test,
but its labels grow with depth, which reintroduces a depth-proportional per-node cost the project
just finished removing, and an interior delete strands a prefix descendants still encode;
Euler tour + RMQ (Bender & Farach-Colton 2000) — O(1) LCA but O(n log n) non-incremental
preprocessing, one fork invalidates the tour; 2-hop / bit-parallel reachability (Cohen 2002,
GRAIL) — the general-DAG answer, and this is a forest: every branch has exactly one parent_id,
written once at fork and never changed. Becomes correct the day a merge commit has two parents.

REAPING: a reaped branch is TOMBSTONED, not removed, because ancestry is genealogy and
reaper.rs:169 walks chains of reaped ancestors on purpose. A tombstone is collected once it is
childless, cascading upward — the same shape as detach_from_parent. Invariant: a node with any
descendant is never physically removed, which is what makes free-list slot reuse safe.

## HOW TO READ THE COLUMNS

  anc_/lca_walk_ns   the parent-pointer walk, over DENSE Vec<u32> arrays — one array index per
                     step, no hashing, no id->slot resolution. This deliberately FLATTERS the
                     walk: the real walk (reaper.rs:169) pays a B+tree descent per step, and the
                     indexed arm pays two HashMap lookups the walk arm does not. Every ratio
                     below is therefore a LOWER BOUND on the gap in the database.
  anc_/lca_index_ns  src/branch/version_graph.rs.
  *_x                walk / index. >1 means the index is faster.
  forkreap_ns        insert one child at depth D then reap it. The column that answers "did you
                     just move the wall onto fork?".
  walk_steps         MEASURED step count of the walk arm. Load-independent, so this and not the
                     clock is what proves the complexity class.
  index_nodes        nodes in the graph; confirms the tree really was built.

Arm order is alternated per depth inside the harness. The harness REFUSES and exits non-zero if
the two arms ever disagree on an answer; all three runs below exited 0, so they agreed at every
depth.

clock corroborates the class; the step count establishes it. See the MECHANISM CHECK section at

## MECHANISM CHECK — the shallow-depth crossover, measured rather than asserted

The reading above claimed the index loses below ~depth 30 "because two HashMap id->slot lookups
cost more than a ten-step walk". That is a mechanism, so it was measured. `depth1hash_ns` times
`VersionGraph::depth`, which is exactly ONE hash lookup and NO climb.

  depth        1 hash    is_ancestor    2 x hash    climb remainder
     10          10.7           21.6        21.4               0.2
    100           9.0           21.1        18.0               3.1
   1000           9.1           24.0        18.2               5.8
  10000          10.0           20.4        20.0               0.4
 100000           8.9           22.6        17.8               4.8

CONFIRMED. One hash lookup is 8.9-10.7 ns and FLAT in depth. Two of them account for 78-99% of
`is_ancestor`; the climb itself is the 0.2-5.8 ns remainder, for 2 array indexings at depth 10 and
up to 17 at depth 100000. The stated mechanism is the right one.

Two consequences worth recording:

  * It explains why `anc_index_ns` reads FLAT rather than logarithmic. The log term is real but is
    a handful of nanoseconds, swamped by a ~19 ns constant that does not vary with depth. The
    curve is flat because of the constant, not because the algorithm is O(1) — it is O(log d).

  * There is ~19 ns of headroom for any caller that already holds slot handles rather than
    `BranchId`s. Not taken here: the API is `BranchId`-shaped because that is what every caller in
    the branch engine holds, and inventing a handle type to win 19 ns on an operation that just
    beat the alternative by 1587x would be optimising the wrong end.
