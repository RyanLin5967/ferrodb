THE PREDICTION, AND IT IS WRONG
-------------------------------
SCALE-NEXT said: "N agents reading their own branches should stay FLAT ... because AgentRuntime
holds one Mutex<State>". Measured at staged=10:

  threads   SHARED total_vs_1T   CONTROL total_vs_1T   SHARED abs   CONTROL abs
        1              1.000                 1.000         1543          1264
        2              1.923                 2.194         2968          2774
        4              3.608                 4.411         5568          5576
        8              6.066                 7.623         9363          9636
       16              9.273                10.913        14312         13796

The shared arm SCALES to x9.273 and at 16 threads is within 4% of the control that removes every
shared structure (14312 vs 13796). The state lock is NOT the wall on this path at this workspace
size. Recorded as a falsified prediction, not defended.

THE REAL WALL, WHICH THE ABSOLUTES POINT AT
-------------------------------------------
1543 stmt/s at ONE thread for an agent-session point read, against 50600 for the identical plain
SELECT in D54 on this box: ~33x slower per statement. src/agent_sql/runtime.rs scan_table builds
`SELECT * FROM t` with where_clause: None and materialises every row; visible_rows overlays the
branch; only then does select apply the statement's WHERE. O(table) per agent read, 5000 rows
here. Same shape as D28 (system views materialise, then filter), at the site every
branch-per-agent read goes through.

THE WORKSPACE WALK, FROM THE PARTIAL AXIS (NOT A MEDIAN)
--------------------------------------------------------
shared 1T at staged=10: 1543 stmt/s.  shared 1T at staged=4000, round 0 only: 973 stmt/s.
So 4000 staged rows cost roughly 37% at one thread -- visible, secondary to the 5000-row base
scan, and to be re-measured to completion before anything is decided about
PersistentMap::range (SCALE-DESIGN D55 option 3).
