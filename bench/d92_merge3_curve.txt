ferrodb D92 — structural three-way merge: the cost curve
=========================================================

WHAT IS BEING CLAIMED

`src/cow/merge3.rs` merges two versions by descending base/ours/theirs together, skipping any
subtree the three agree on. The claim is a COMPLEXITY CLASS: the descent costs O(delta x log N)
page reads, not O(N). Everything below is an operation COUNT, never a wall clock — this box was
running ten agents while these numbers were taken, and a count reads the same on a loaded machine
as on an idle one. That is the only reason a number measured here is worth banking.

THE RESULT IN ONE LINE

    N x256  ->  pages x257.9,  nodes_read x2.40 (contested) / x1.91 (separated).

At N = 256,000 the merge read 36 pages of a 16,250-page tree (0.22%) in the contested workload and
21 (0.13%) in the separated one. `nodes_read / depth` is flat.

REPRODUCIBILITY

Every count below came out IDENTICAL on three independent runs of this harness, built from three
different commits of this branch (6ac68d8, 9fef21c, 8164089), on a box whose load average moved
between 24 and 45 across them. The only line that differed between runs is MerkleId's own cost,
because that implementation changed. Operation counts do this; wall clocks do not, which is why
there is not a single timing in this file.

HOW TO FALSIFY IT

Read the `pages` and `nodes_read` columns. If the merge were O(N) they would grow by the same
factor. The prediction is that `pages` grows ~256x across the size axis and `nodes_read` grows by
roughly the ratio of the tree DEPTHS — about 2x. `nodes_read / depth` should be flat.

WHAT THE INSTRUMENT IS

`MergeStats`, returned by `merge3` itself:
  nodes_read           page reads the descent issued, DEDUPLICATED WITHIN EACH NODE TRIPLE AND
                       NOT GLOBALLY. Within the triple, because over most of a merge `base` and
                       `ours` are literally the same page id and counting that page twice would
                       inflate this file's own y-axis by half. Not globally, because a node
                       reached from two bands is two real reads.
  ids_compared         identity comparisons. Free for ShadowId (it IS the page id), so this is CPU
                       and not I/O. Reported separately and never folded into nodes_read.
  skip_sides_agree     subtrees retired by `ours == theirs` (subsumes all-three-equal).
  skip_theirs_unch     subtrees retired by `theirs == base`.
  descend_ours_unch    subtrees where `ours == base`: NOT a skip, a two-way descent.

ANTI-VACUITY

Three separate checks, all asserted inside the harness so a bad run fails rather than prints:
  1. Every arm asserts `root_fast_path == None`. A root-level O(1) rule would retire the whole
     merge and the arm would have measured nothing.
  2. Every arm reads back the merged tree: all 8 changed keys, plus a 512-point sample of
     untouched keys. A curve over a WRONG merge is worse than no curve.
  3. The skip counters are shown to fire AND not to fire. See the counter fire-check and the
     detector fire-check below.

WHAT THIS REPLACES, AND WHAT IT DOES NOT

`CowTree::diff(base, head)` already existed and is honest in its own doc that its page-IDENTITY
traversal is proportional to the tree: it calls `walk_pages` on BOTH roots in full, into two
HashSets, before it can prune either against the other, and `walk_pages` issues a `read_page` for
every page it visits including leaves (src/cow/btree.rs:136). Its `pages_examined` counter reports
only the second half — the entry DECODING — which is why that number looks small next to the work
the call actually does.

So a merge assembled from two diffs would read, before pruning anything:

    pages(base) + pages(ours)  +  pages(base) + pages(theirs)     ~= 3 x pages

DERIVED, NOT MEASURED — the arithmetic is from the `pages` column above and from reading
`walk_pages`; no diff-based merge was built or timed. At N = 256,000 that is roughly 48,750 page
reads against the 36 that `merge3` took. The difference is not a constant factor to be optimised
away later: it is the difference between pruning after two full traversals and pruning at the
moment of comparison, which is the whole reason the descent is synchronised.

WHAT OP-REPLAY STILL DOES BETTER, AND IT IS NOT CLOSE

`agent_sql::runtime` merges by replaying recorded ops, and that is NOT superseded. `OpKind` is an
effect algebra: a counter at base 10 with ours `Add(5)` and theirs `Add(3)` composes to `Add(8)`
and merges CLEAN at 18. A structural merge sees 10 / 15 / 13 — three distinct values, one cell,
both sides moved it — and by row 5 of the truth table that is a CONFLICT with no repair available,
because the information that 15 *meant* "+5" was never in the tree. Same for a set-valued column:
op-replay unions two `SetInsert`s under observed-remove semantics, structural sees two different
blobs and conflicts.

The two are complements. Op-replay cannot merge what it did not record and is O(ops since the fork)
over a log that is never pruned; structural needs only the three trees at rest, is O(delta x log N),
and can therefore AUDIT an op-replay result — but it cannot merge what the values do not say.

READING THE NUMBERS BACK

Every count above is arithmetically checkable by hand, which is the point of an operation count.
Worked example, contested arm at N = 1,000 (depth 2): the root triple reads 3 distinct pages; four
leaf triples read 3 each; 3 + 12 = 15, which is what `nodes_read` says. At depth 4 the same
accounting gives the mid-level reads, minus the nodes the four paths share on the way down.

ONE CONTENT IDENTITY, AND WHAT IT COST

`MerkleId` used to carry a private 128-bit mixer inside `merge3.rs`. D89 landed `src/cow/cid.rs`
with `Cid = [u8; 16]` and `subtree_cid(tree, page)` answering the same question, so the tree held
two 16-byte content identities that disagreed byte for byte. The mixer is deleted and `MerkleId`
now calls `subtree_cid`; `merkle_id_returns_exactly_what_cid_subtree_cid_returns` checks that over
every page of a 300-key tree, and checks that a second pass costs zero additional walks.

That cost 3x, and the identity section above prints it rather than burying it: `subtree_cid` has no
memo INSIDE its recursion, so the three roots re-read almost the same pages — about 3,048 reads over
a 1,016-page tree, where the deleted mixer's per-page memo touched 1,022. The trade was taken on
purpose. Two content identities that disagree will be compared eventually and that failure is
silent; 3x on a path this curve does not even use is not.
