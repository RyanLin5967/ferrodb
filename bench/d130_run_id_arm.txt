2. ARM D IS A BATCH RACE — ITS CELLS MOVE WITHOUT ANY KNOB CHANGING
================================================================================

A first draft of the pre-registration said arm D 'MUST read the same in both
modes'. It was caught by this smoke pass and corrected BEFORE the arm had any
evidence in it. Arm D calls TableBranchCatalog::fork directly, builds no
RunEntity and reads no environment, so no code path carries either knob into
it — but it is itself a batch race, which is the reason it exists.

30 consecutive runs at the IDENTICAL default knob, ladder 4 1,2, arm D only:
    30  T=1 forks=4 syncs=4 f/sync=1.00
     1  T=2 forks=8 syncs=6 f/sync=1.33
     4  T=2 forks=8 syncs=7 f/sync=1.14
    25  T=2 forks=8 syncs=8 f/sync=1.00

So a single shared-mode cell reading 7 sits inside the DEFAULT arm's own
distribution. The invariant is that arm D shows no reproducible TREND across
modes — not that any one cell matches.

    P  conn per fork, BEGIN only          2        8        8      1.00     0.5000   prov.log=109B

  ⭐ prov.log under durable is the mechanism, stated by the store itself:
       distinct:  412B at 4 forks, 816B at 8 forks   — LINEAR in forks,
                  one appended+fsynced frame per fork.
       shared:    109B at 4 forks, 109B at 8 forks   — CONSTANT, exactly one
                  frame for the whole cell.
     That is DurableProvenanceStore::intern taking its repeat path
     (`if self.mem.run_count() == before { return Ok(id); }`) and never
     reaching append_locked's file.sync_data().

  ⛔ Under mem there is no prov.log at all and no fsync to remove, which is why
     mem x shared is the arm's NEGATIVE CONTROL rather than its test.

4. FIRE CHECK — EVERY REFUSAL FORCED TO FIRE
================================================================================

A guard that has never fired is not a guard. Each mutation below was applied to
the committed source, built, and run; the tree was restored with
`git checkout --` after each. M4's first attempt used a pattern that did not
match, so the mutation never landed and the run passed — recorded here because
a non-matching mutation looks exactly like a dead guard, and it was re-run with
a shasum check proving the edit landed before the result was believed.

  M1  shared mode emits distinct ids instead of the pinned tuple
      -> REFUSING ... D130_RUN_ID=shared pins every fork to run id `r0_0`, but
         the server echoed 4 distinct ids: {"r0_0","r0_1","r0_2","r0_3"}    exit 1

  M2  shared mode drops one run-id echo per thread
      -> REFUSING ... asked for 4 forks but the server echoed a run id 3
         times.                                                            exit 1

  M3  [PRE-EXISTING] branch names not counted (named += 0)
      -> REFUSING ... 4 statements returned 0 branch names.                exit 1

  M4  [PRE-EXISTING] sync counter frozen (let after = before)
      -> REFUSING ... the catalog issued 0 fsyncs across 4 forks.          exit 1
         (mutation landed: faf302e9 -> f52df8d7)

  M5  D130_PROV=durable made a no-op (builder never applied)
      -> REFUSING ... D130_PROV=durable, but .../prov.log does not exist.
         The runtime is still on MemProvenanceStore, so the knob did
         nothing and every `durable` cell in this run is mislabelled.      exit 1

  M6  shared mode mints a second entity (agent alternates a0/a1)
      -> REFUSING ... the store holds a SECOND entity at ProvId(2) after 4
         forks. `intern` minted a new run instead of taking its repeat
         path.                                                             exit 1

  And the knobs themselves refuse an unrecognised value rather than defaulting:
      D130_RUN_ID=bogus -> REFUSING ... is neither `distinct` nor `shared`. exit 1
      (bench/d130_run.sh validates both knobs ABOVE the suite lock, so a typo
       cannot spend a fifteen-minute hold to discover itself.)

  The two guards the dispatch brief named as untouchable — the sync counter not
  moving (M4) and the server naming a different branch count than the clients
  asked for (M3) — both still fire, and were forced to fire on the NEW shared
  path rather than only on the default one.

5. THE COMMAND FOR THE REAL SWEEP
================================================================================

Four runs, each taking the suite lock in turn. The direct phase is identical in
all four (fork_concurrency reads neither knob), so it is run once and the other
three are pgwire-only and APPEND:

  bench/d130_run.sh bench/d130_s5_run_id_arm.txt 3 1
  PHASES=pgwire APPEND=1 D130_RUN_ID=shared \
      bench/d130_run.sh bench/d130_s5_run_id_arm.txt 3 1
  PHASES=pgwire APPEND=1 D130_PROV=durable \
      bench/d130_run.sh bench/d130_s5_run_id_arm.txt 3 1
  PHASES=pgwire APPEND=1 D130_PROV=durable D130_RUN_ID=shared \
      bench/d130_run.sh bench/d130_s5_run_id_arm.txt 3 1

Defaults are the pre-registration: TLIST=1,2,4,8,16,32,64,128, PGWIRE_F=40.
Read A/B/C off the durable pair. mem x shared is the negative control and must
not move f/sync; if it does, the knob is doing something it does not claim and
every other cell is suspect.
