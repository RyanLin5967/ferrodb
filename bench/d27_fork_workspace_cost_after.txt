D27: the fork's workspace cost, BEFORE and AFTER structural sharing.

Instrument: examples/d27_fork_workspace_cost.rs, release build, one configuration per process.
  us_per_fork    -- std::time::Instant around the begin_session loop ONLY.
  fork_rss_MB    -- getrusage ru_maxrss after the fork loop minus before it.
  stage_s        -- the parent's UPDATE staging W rows into an UNSHARED workspace map.
  child_write_s  -- a child's UPDATE over W rows into a map SHARED with parent + N-1 siblings.
  seed_s         -- W trunk INSERTs. This path is NOT touched by the change; it is reported
                    because it is the noise gauge (see CAVEAT).
Both arms were run back to back on the same machine, from the same binary source, with only
src/agent_sql/{runtime,mod}.rs stashed between them. BEFORE reproduces the earlier
bench/d27_fork_workspace_cost_before.txt run (fork_rss 6.3/25.9/104.3/417.7 vs 5.8/25.3/103.9/417.0).

INTERPRETATION (written after the numbers, not before):

1. THE PREMISE HELD: the cost was O(N·W), and memory is the cleanest instrument that says so.
   Divide fork_rss by N·W and BEFORE gives a constant across every configuration --
   393.8, 404.7, 407.4, 407.9, 418.8, 406.2, 403.1, 400.4, 403.7 bytes per copied row.
   Nine cells spanning 16000..4096000 row-copies, spread of 6%. That is not a trend line fitted
   to noise; it is one number. AFTER, the same quotient is 0.0-12.5 bytes, which is the 0.1 MB
   quantisation of ru_maxrss rather than a measurement of anything.

2. THE FORK IS NOW O(1) IN W, WHICH IS THE ACTUAL CLAIM. Speedup ratios are the eye-catching
   number but the SHAPE is the real result. At fixed N=64, sweeping W from 250 to 4000:
     BEFORE  22.876 -> 34.785 -> 66.680 -> 136.598 -> 347.782 us/fork  (15.2x for 16x the work)
     AFTER    1.044 ->  0.902 ->  0.868 ->   0.928 ->   1.273 us/fork  (no trend at all)
   Before, a fork cost what the parent's working set cost. After, it does not depend on it. The
   ~1 us that remains is the rest of `begin_session` -- interning the run, forking the branch
   record, inserting the name -- so the five maps have left the critical path entirely.

3. THE WALL AT THE 10^6 OBJECTIVE, QUANTIFIED. At 404 bytes per copied row, one parent holding a
   thousand staged rows with 10^6 children is 10^9 row copies = ~404 GB of resident memory, which
   is why this was a wall and not a slow path. The measured 1024-child, 4000-row cell already
   costs 1.65 GB. After: 1.6 MB.

4. WHAT IT COST, STATED PLAINLY. Writes got slower, because an insert now allocates the ~log2(W)
   nodes on its root-to-leaf path instead of updating a BTreeMap in place. `stage_s` is slower in
   9 cells out of 9 -- 1.21x, 1.36x, 1.50x, 1.67x, 1.67x, 1.75x, 1.83x, 1.84x, 1.98x -- and
   `child_write_s` in 7 of 9. Nine out of nine in the same direction is not noise, so the
   regression is real. In absolute terms the worst cell is a 4000-row statement going from
   2.9 ms to 5.8 ms. That is the trade: ~2x on the staging path, against 443x on fork latency and
   1034x on fork memory. It is the right way round for an agent workload, where one parent is
   forked many times and each statement is staged once -- but it IS a cost, and a workload that
   staged huge statements and never forked would be worse off.

CAVEAT -- how much of the wall clock to trust. `seed_s` measures W trunk INSERTs, a path this
change does not touch at all, and it moved 24.268 -> 45.751 between the two arms at W=4000. That
is a ~1.9x swing from machine contention alone (a fleet of other agents was building and testing
on this machine throughout). So: treat individual wall-clock ratios as approximate, and treat
the 1.21x-1.98x write regression as "real in direction, uncertain in magnitude". The two results
that do NOT depend on wall clock are the memory column and the flatness of us_per_fork against W,
and those are the ones the conclusions above rest on.
