D98 — the outer RuntimeLock held across a whole lease sweep, measured before and after.

WHAT THIS ROW IS ABOUT. `branch::lease_thread::scan_once` ran its entire body inside one
`with_lock(..)`, and in both production shapes that lock is the mutex every SQL statement takes:
`ServerContext::catalog` for the pgwire server, `CatalogLock` for the CLI. So the stall on every
connection was the length of one sweep, and a sweep is O(branches that expired on this tick) —
which in an agent fleet is O(agents). W4's earlier rows are about `AgentRuntime`'s INNER
`Mutex<State>` and say nothing about this lock; `bench/w4/DECISION.md` addendum 1 says so and its
closing section lists this one as still open. Nothing had measured it.

REPORT THIS AS A SHAPE, NOT AS A SCORE. A lock held across work proportional to the branch count
serializes writers in ANY engine that sweeps under a statement lock. That is BranchBench's named
open problem (arXiv:2604.17180, Fig. 4: "serialization bottlenecks in control-plane operations"),
and the shape is what transfers off ferrodb. The absolute microseconds do not: a favourable
number here is partly an artifact of what ferrodb does not yet do, and ferrodb is a proof of
concept, not a competitor. Nothing below is a claim about beating any system.

TWO KINDS OF NUMBER, AND THEY ARE NOT EQUALLY TRUSTWORTHY.
  COUNTS    `reap/acq` (branches reaped per acquisition of the statement lock) and `done_in_sw`
            (client statements that COMPLETED while the sweep ran). Integers. Fleet load does not
            change how many times a lock was taken. THE CLAIM RESTS ON THESE.
  DURATIONS p50/p99/max client latency. Real, and UPPER BOUNDS — every one is inflated by whatever
            the fleet was doing. `load_at_acquire` is stamped below for each round.

HOW IT WAS TAKEN. `examples/outer_runtime_lock.rs`, driven by `bench/d98_run.sh`. Two builds of
the SAME harness differing only in `src/`, run alternately (A B B A) inside the fleet measure lock,
which was taken per round so a 45-minute stale-owner steal could not land mid-measurement. Arm
order inside each invocation rotates with the rep index. Five arms per fixture:
  idle   — no sweep at all. The negative control and this machine's floor.
  locked — the production wiring: the sweep is handed the ServerContext whose mutex the clients
           are taking. The thing under test.
  free   — same N, same K, the identical sweep work, under a PRIVATE mutex nobody else holds.
           THE CONTROL THAT COULD HAVE WITHDRAWN THE CLAIM: 10^5 branches is more resident state
           whatever the lock does, so if `free` degraded with N too, the result would be residency
           and not the lock.
Two K series, because "grows with branch count" has two candidate mechanisms and one series cannot
separate them: K_prop = N/100 rises with N (the agent workload), K_fixed = 64 does not (isolating
any cost that is a function of TOTAL branches, e.g. the deadline-index descent).

The harness REFUSES rather than reports: a cell whose sweep reaped nothing, a cell no probe
overlapped, and an arm the fixture could not give its full K all print `--` and exit non-zero.
All eight invocations exited 0 with every cell measured.
