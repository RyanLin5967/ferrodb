Slower forks at a FIXED fork count means each fork takes longer, so more forks
accumulate behind a leader's fsync, so the BATCH IS LARGER. That is exactly the
model this script's own "WHY THE LOCK" comment names: min(1/S, T/D), where
contention raises the fsync latency D and the batch is T/D-bounded.

⛔ SO `f/sync` IS NOT LOAD-IMMUNE, AND examples/d130_pgwire_batch.rs's header
   OVERSTATES IT. The header says it is "a ratio of two counters taken by one
   instrument over one run, so it is load-immune". That is true of measurement
   ERROR — the ratio needs no clock — and FALSE of the QUANTITY: batch size is a
   function of fsync latency, which load moves. The run script's WHY THE LOCK
   comment has this right; the harness header does not.
   And the suite lock does not protect against it: a teammate's `cargo build`
   contends for the same device without ever taking the suite lock.
