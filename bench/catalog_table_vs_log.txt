UNINTERPRETED NOTES, and the caveats are not decoration:

1. TOTAL TIME IS NOT COMPARABLE between the two arms and no ratio should be quoted from it. The
   log catalog fsyncs every append; the table catalog writes through the buffer pool and is
   flushed once at the end. Equalise durability before comparing seconds.
2. DISK IS 3.7x LARGER and that is inherent, not a defect to fix later: each branch writes four
   entries (core record, state, deadline, child) instead of one 68-byte log record, and a B+tree
   carries page fill factor on top. Predicted ~136 B of entries at ~50% fill = ~270; measured 250.
3. The residency marginal is no longer "one record resident per branch". 15.2 B/branch is page
   table bookkeeping over a file that grew 4x; it is not a smaller version of the same term.
4. 10^6 is NOT MEASURED. Extrapolating the marginals gives ~636 MB for the log and ~15 MB for the
   table, and an extrapolation is not a measurement.
5. AN EARLIER VERSION OF THIS CURVE WAS WRONG AND LOOKED BETTER. The first table-arm run reported
   a perfectly flat 7.09/7.16/7.09/7.13 MB. It was flat because the process PANICKED a few
   thousand forks in - `range end index 4100 out of range for slice of length 4096`, an internal
   B+tree node overflowing its page - so the same startup cost was measured four times. The
   pipeline's exit status came from the trailing grep, so nothing failed loudly. The harness loop
   now REFUSES when a run produces no data line. The bug is fixed in 549b9a7 and is pre-existing:
   it is reachable by any user table with enough rows.
