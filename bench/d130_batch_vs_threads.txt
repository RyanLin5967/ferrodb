--------------------------------------------------------------------------------
1. THE DECISIVE NUMBER IS T=64 → T=128, AND IT IS A COUNT
--------------------------------------------------------------------------------

Doubling the thread count from 64 to 128 moved the direct-layer batch from 17.08 to
17.61 forks per fsync: **+3.1%**. A batch set by the thread count would have doubled.
The batch SATURATES, and it saturates at a value this sweep measures: C ≈ 17.6.

That is the whole of outcome 2, and it needed T=128 to see. At T=64 alone — the only T
this project had before this run — `f/sync ÷ T` is 0.267, and a single point cannot tell
a saturating curve from a rising one.

--------------------------------------------------------------------------------
2. THE `T/2` LAW IS REAL, AND IT IS NOT THE CEILING
--------------------------------------------------------------------------------

The sweep does NOT kill the wake-up race. Below the knee the direct layer tracks `T/2`
to within 9%:

      T      f/sync    T/2    ratio
      2        1.00      1     1.00
      4        1.99      2     0.99
      8        3.91      4     0.98
     16        7.32      8     0.92
     32       12.61     16     0.79      ← the knee
     64       17.08     32     0.53
    128       17.61     64     0.28

⇒ The batch is `max(1, min(T/2, C))` with C ≈ 17.6 measured here. The race governs while
  `T/2 < C`; above it the serial section does, and `T` stops appearing in the answer.

⇒ ⭐ SO THE ROW'S HEADLINE IS WRONG WHERE IT MATTERS AND RIGHT WHERE IT DOES NOT. "The
  batch is EXACTLY HALF THE THREAD COUNT" holds for T ≤ 16 and fails at T = 64 (0.267)
  and T = 128 (0.138) — and 64 is the operating point every other number in this project
  is quoted at.

--------------------------------------------------------------------------------
4. AT THE LAYER PRODUCTION RUNS, THERE IS NO GROUP COMMIT AT ALL
--------------------------------------------------------------------------------

`f/sync` is **1.00 at every T from 1 to 128** in arm P, with `syncs` exactly equal to
`forks` at every cell (40/40, 80/80, … 5120/5120). Not approximately: exactly. Every
`BEGIN AGENT SESSION` over the wire pays a private fsync and shares it with nobody, at
128 concurrent connections as at one.

Arm S is the control for the obvious objection — that arm P's threads spend their time
connecting rather than queueing, so few are ever inside `wait_durable` together. Arm S
keeps one connection per thread and returns to the fork immediately. It reads **0.20 at
every T**, exactly 1/5 (five catalog fsyncs per BEGIN+ABANDON cycle), and just as flat.
⇒ The connection shape is not the reason. Neither arm batches anything.

The mechanism is the second alternative outcome 2 names — *"an fsync that is not the
serialization point at all"*. `ServerContext::catalog()` is taken outermost for the
duration of one statement, `try_run_read` admits only EXPLAIN and non-`AS OF` SELECT, and
the fork statement is not among them. So no two forks are ever concurrently inside
`wait_durable` and there is never a group to commit. This is an independent, load-immune
confirmation of what E.6 measured with lock counts and what W4 §"the outer lock" reads
off the source.

⇒ ⭐ THE GROUP-COMMIT MECHANISM THE 21×/1.9× PAIR IS ABOUT IS INVISIBLE TO ANYTHING THAT
  CONNECTS OVER THE WIRE.

--------------------------------------------------------------------------------
5. WHAT THIS LICENSES — AND WHAT IT DOES NOT
--------------------------------------------------------------------------------

⛔ **STAGED GROUP COMMIT IS NOT LICENSED BY THIS RESULT, AND MUST NOT BE PROPOSED ON IT.**
The entry pre-wrote that fix for outcome 1, with its prior art named (PostgreSQL's
`commit_delay`/`commit_siblings`; MySQL 5.6 / MariaDB binlog group commit split into
flush/sync/commit stages, Kristian Nielsen; ARIES 1992; RocksDB's write-batch leader).
Outcome 1 did not fire. Staging lifts the batch from `T/2` toward `T` only where `T/2` is
the binding term — T ≤ 16 here — and at T ≥ 64 the batch is capped at C ≈ 17.6 by the
serial section, so staging buys nothing at the operating point. At the pgwire layer it
buys nothing at any T, because there is no group to stage.

✅ What the counts do license, both of it engineering this project has already named:

  (a) DIRECT LAYER — the lever is C, and C is `D/S`: the number of forks that can pass
      through `logical` during one fsync. Shortening the serial section is the only thing
      that moves it above the knee. This is not new either: `bench/fork_concurrency_after.txt`
      already concluded *"the batch size is not set by the disk at all — it is set by HOW
      MANY FORKS CAN GET THROUGH `logical` WHILE ONE FSYNC RUNS"*, from a T=64-vs-T=256
      pair. This sweep confirms it across eight values of T and locates the knee at T ≈ 2C.

  (b) PGWIRE LAYER — the lever is the outer statement lock, and the change is already
      written down as W4 falsifier 3: *"Does the fork statement (`BEGIN AGENT SESSION`)
      need `&mut Catalog` at all? It is not DML. If it does not, it may be admissible to
      `try_run_read` independently of DML — a much smaller change that directly answers
      E.6."* Until something like that lands, no amount of work on `group_commit.rs`
      changes a single number a client can observe.

⇒ ⭐ THE FINDING IS THE CORRECTION, NOT A MECHANISM. The most-cited quantity in this
  project is a batch that saturates at ~17.6 and a wire layer where it is 1.00, and
  candidates have been designed against `T/D` as though `T` were in the numerator. It is,
  but only below T ≈ 32, and never at all through pgwire.

--------------------------------------------------------------------------------
6. SUBORDINATE CROSS-CHECK — NOT EVIDENCE FOR THE OUTCOME
--------------------------------------------------------------------------------

The outcome above rests on counts alone. This paragraph is a consistency check and is
flagged as one, because the box is shared and every duration on it is an upper bound.

If C is `D/S`, then the single-thread per-fork cost is `D + S` and the saturated
per-fork cost is `S`. Rep 1: 3.684 ms at T=1, 0.209 ms at T=128 ⇒ S ≈ 0.209, D ≈ 3.475,
`D/S` ≈ 16.6 against a measured batch of 17.6 — 6% apart, in the direction the upper
bound predicts. It is consistent with C = D/S and it is not offered as proof of it.
