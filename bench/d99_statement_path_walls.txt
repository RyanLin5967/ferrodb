--------------------------------------------------------------------------------
THE INTEGER AXIS — the claim; durations are only confirmation
--------------------------------------------------------------------------------
This box never goes quiet, so a duration is an upper bound and nothing better.
The complexity claim therefore rests on an integer that no amount of fleet load
can move:

    scan_steps = len(st.current) = entries the REPLACED `retain` visits per call

That is `HashMap::retain`'s contract — it visits every entry — so it is
arithmetic, not a measurement:

      branches M      scan_steps (BEFORE, per free_arena)    AFTER
           1,000                              1,001          1 hash probe
          10,000                             10,001          1 hash probe
         100,000                            100,001          1 hash probe
       1,000,000                          1,000,001          1 hash probe

The M term is gone. Everything below is confirmation that nothing else replaced
it.

--------------------------------------------------------------------------------
WHY EVERY ARM PADS ONE COUNTER AND HOLDS THE OTHERS DOWN
--------------------------------------------------------------------------------
D77 named ONE scan in `free_arena`. Reading it found FOUR linear-or-worse steps
in series in that one function:

  1. `for i in 0..pages { evict(..) }`          O(pages in THIS extent) — constant
  2. `st.pending.retain(|p| ..)`                O(len(pending))
  3. `st.current.retain(|_, a| *a != arena)`    O(BRANCHES)  <- the named wall
  4. `persist_if_configured()` -> `state_bytes()`  sorts AND serialises every
     extent and every `current` entry, then writes the file.

Walls in series are indistinguishable from one wall twice as big, so each arm
moves ONE axis. Step 4 is not hypothetical — `cli.rs` and `examples/pgserver.rs`
both call `checkpoint_to`.

Two corrections to D77's row, both found by reading before measuring:
  * The line numbers are stale. `arena.rs:1316` is a COMMENT inside
    `alloc_arena`; `free_arena` begins at 1391 and the scan was at 1414.
  * Neither wall is on the statement path as stated. `free_arena`'s only
    non-test callers are in `reaper.rs`, driven by `lease_thread.rs`. It reaches
    statements INDIRECTLY: it does its linear work while holding `self.state`,
    the lock every statement's `arena_for` also takes. That is the D88 shape and
    a real coupling, but it is not a direct per-statement cost.

--------------------------------------------------------------------------------
`register_reader` is called once per TCP CONNECTION (pgwire/mod.rs, startup
path) and the registry self-cleans by refcount. Its N is live connections; the
branch count does not enter it anywhere.

A2  ServerContext::catalog() vs BRANCHES. Readers fixed at 8. Batched.
      branches M    live_count    ns/catalog()
          1000         1001           28.24
         10000        10001           25.63
        100000       100001           25.61
       1000000      1000001           24.41

Flat — and slightly falling — across four decades, out to the 10^6 branches this
project's objective is stated in. These are real sub-tick numbers, visible only
because the arm times a batch. The padding is the SAME padding that produces
B1's 1,000,001 scan_steps, so a flat A2 beside a loaded B1 is evidence about the
code and not about padding that failed to happen.

⇒ NOT a branch-count wall. Stopped, per the row's own rule.

It IS a real O(connections) wall, measured:

A1  ServerContext::catalog() vs REGISTERED READERS. Branches: 0. Batched.
      readers C     ns/catalog()      ns per 1000 C
          1000          1886.8           1886.83
         10000         30934.2           3093.42
        100000        304551.4           3045.51

Linear in C (per-1000 flattens at ~3,000 ns). Two notes for whoever takes that
axis, neither acted on here because this row is scoped to branch count:
  * The header disagrees with the body. The comment at mod.rs:137 says "the scan
    is N atomic loads over live connections". The body CLONES the Vec<Arc<..>>
    under the lock — N atomic increments, then N decrements when `slots` drops.

THE FIX (src/branch/arena.rs, in free_arena)
  - st.current.retain(|_, a| *a != arena);
  + if st.current.get(&ext.owner) == Some(&arena) { st.current.remove(&ext.owner); }

Re-indexing the question, not speeding up the answer — the shape of the reaper's
deadline-ordered index and of D86's `applied_by_cell`. Here the index already
existed and was being discarded: `ArenaExtent.owner` names the branch, and the
line above the scan read `let _ = ext;` to silence it.

Equivalence rests on arena ids never being recycled.
`ArenaSpaceManager::reserve` draws every id from a monotonic counter
(`arena_ids.take(1)`); `give_back` recycles only the page RANGE. So an id names
one extent for the store's life and cannot be reissued under a second owner, and
`alloc_arena` writes `extents[arena].owner = branch` and `current[branch] =
arena` inside ONE critical section. Therefore if any branch maps to this arena it
is `ext.owner` and no other. The `get` guard keeps the case the `retain` also
handled: an owner that has moved to a newer extent has `current[owner] != arena`
and neither spelling touches it.

ALSO FIXED on the same path: `free_arena` cleaned every per-arena map except
`fill_unknown`. `load_state` seeds that set with EVERY restored extent and only
`resolve_fill` ever clears an id — which nothing calls for an extent that no
longer exists — and since arena ids are never reissued, a leaked suspicion could
never be collected by any later path. Not a correctness bug (`extent_is_empty`
already answers false for a missing extent, so the stale entry changes no
decision), but per-arena state left behind by the path whose job is to give
per-arena state back.

(b') WHAT IS STILL LINEAR — AND WHY THE FIX ABOVE BARELY MATTERS IN PRODUCTION
--------------------------------------------------------------------------------
B2  free_arena vs PENDING. branches=1000, persist OFF. AFTER (9c9d26f).
    NOT a clean control at the low end: branches are padded to 1000, so the
    branch-axis fix moves the P=1k row too. It is a control where P dominates.
      pending P    verified    ns/free_arena    ns per 1000 P
          1000        100           417.0           417.00
         10000        100          3666.0           366.60
        100000        100         35833.0           358.33
       1000000        100        529167.0           529.17

`st.pending.retain` is O(len(pending)) and remains so: 529 us per free_arena at
P=10^6. Untouched by this row, and a second wall in series on a different axis.

B3  free_arena vs BRANCHES, persist ON — the configuration cli.rs ships.
    AFTER (9c9d26f). Persistence enabled AFTER padding (see defect 2).
      branches M   scan_steps   verified   ns/free_arena      map bytes
          1000         1001         50      24,987,792         48,089
         10000        10001         50      26,864,500        480,089
        100000       100001         50      64,817,542      4,800,089
       1000000      1000001         50     846,991,666     48,000,089

⇒ 847 MILLISECONDS per free_arena at 10^6 branches. And it is NOT a constant:
  25.0 -> 26.9 -> 64.8 -> 847 ms. Below ~10^4 branches a ~25 ms fsync floor
  dominates; above it the sort-and-serialise term takes over and the last decade
  costs 13x for 10x the branches. The map is 48 bytes per branch, exactly
  linear, and `state_bytes` sorts it — so step 4 is an O(M log M) wall on the
  free path, and it is the REAL one.

  rev1 called this "an fsync-dominated CONSTANT" on the strength of two points
  that fell 21% (66.4 -> 52.4 ms). That reading was wrong and the two points
  were themselves corrupted by defect 2. Retracted.

  THE HONEST CONSEQUENCE. At 10^6 branches the scan this row removed cost
  458 ns inside a call that pays 847 ms to persist — about 1 part in 1.8
  million. The fix is correct and removes a genuine O(branches) term from under
  the store's hottest lock, but anyone quoting a speedup for the shipped server
  will not find one, and a before/after taken with persistence ON would have
  shown nothing at all. Same trap D79 caught this project in: every 10^6 result
  published here had persistence OFF.

  The next wall on this path is step 4, and it is a rewrite of how the
  free-space map reaches disk — incremental or append-only rather than
  whole-map-per-free — not a scan to re-index. It touches `state_bytes`, the v3
  image format and `put_pending`'s durability contract, all shared with
  `alloc_arena` and the reaper. NOT attempted here: outside this row's file
  ownership and outside its scope.

INSTRUMENT DEFECTS FOUND IN REV 1, AND WHAT REPLACED THEM
--------------------------------------------------------------------------------
1. SINGLE-CALL TIMING AGAINST A 41 ns CLOCK. rev1's A2 reported "42.0 ns" at
   four branch counts and read it as constancy. It is one clock tick. The
   refutation of wall (a) survives — a cost growing with M would have crossed
   into the next tick and did not — but the precision claim does not. Every arm
   now brackets a batch; T0 measures and prints the tick.
2. B3 CONFIGURED `checkpoint_to` BEFORE PADDING, so each of the M `arena_for`
   calls in setup rewrote the whole map: O(M^2) setup. rev1's "could not be
   collected inside 900 s" was `pad_branches` timing out, reported against
   `free_arena`. Persistence is now switched on after padding, and B3 reaches
   10^6.
3. `freed` COUNTED `free_arena`'s NO-OP `Ok(0)` AS A SUCCESS, so the `freed==0`
   refusal was satisfied by exactly the case it existed to reject. Frees are now
   verified by ownership before and after the call. (`Ok(0)` is also the honest
   return for a real free of an extent with no allocated pages — which is what
   `arena_for` padding produces — so the return value cannot be the test and is
   not used as one.)
4. B2 WAS LABELLED "(Control: untouched)" while its own first row moved 3.8x.
   It is a control only where P dominates; relabelled.
5. B3 WAS BEFORE-ONLY DATA PRESENTED WITHOUT ITS ARM. Every row now carries one.

--------------------------------------------------------------------------------
WHERE THIS MEASUREMENT COULD STILL BE WRONG
--------------------------------------------------------------------------------
* The padding catalog is `LogBranchCatalog::in_memory`, not the shipped
  `TableBranchCatalog`. `free_arena` never reads the catalog — it touches
  extents/recycled/pending/claim_epoch/current/fill_unknown, `give_back`, the
  counters and the persist — so the catalog is setup cost only. It was switched
  because TableBranchCatalog forks at ~29 ms each (1,000 forks in 28.7 s wall at
  2% CPU, fsync-bound), putting 10^6 out of reach for a reason unrelated to the
  wall. CROSS-CHECKED, not assumed: B1 at M=1,000 measured 959 ns on
  TableBranchCatalog and 1,000 ns on the in-memory one under the rev1
  instrument. `D99_CATALOG=table` reruns any arm.
* Durations were taken under load 16-17 with exclusivity against other measurers
  but not against the build fleet. They are upper bounds. The integer column is
  not affected by this and is the load-bearing evidence.
* B1's AFTER residual (84 -> 458 ns over 1,000x M) is attributed to cache/TLB
  pressure. That attribution is an inference from the shape, not a measurement;
  no profiler was run. What IS measured is that it is not linear in M.
* Every arm refuses rather than printing a number it cannot attribute: zero
  iterations, zero VERIFIED frees, or padding that did not take (`live_count`
  below M, `pending_len` != P) print NOT A RESULT.
