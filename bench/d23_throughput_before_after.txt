INSERT  best-of, BEFORE: 80602 / 75717 / 71475 / 82056   (range 71475-82056)
INSERT  best-of, AFTER : 75959 / 77617 / 74015 / 72332   (range 72332-77617)
  -> NO RESOLVABLE DIFFERENCE. The ranges overlap heavily; AFTER's best (77617) beats two of the
     four BEFORE passes. The first pass's "5.7% slower" was noise. What can be said with this
     instrument: the latch does not halve uncontended insert throughput, and any cost is small
     enough that 4 passes of 40k inserts cannot separate it from run-to-run variation on a machine
     running an agent fleet. An upper bound of roughly 5% is the honest claim; the point estimate
     is not resolved. Medians are WORSE behaved than best-of here (AFTER ranged 53203-71650), which
     is what you expect when the noise is external load rather than the code.

SEARCH  best-of, BEFORE: 207387 / 208991 / 219454 / 212373  (range 207387-219454)
SEARCH  best-of, AFTER : 298143 / 301637 / 313196 / 298727  (range 298143-313196)
  -> +43%, and the two ranges DO NOT OVERLAP. This is a real effect.

  ** It is NOT caused by latching, and must not be reported as a benefit of it. ** Verified in the
  source, not inferred from the number: the pre-latch `search` did the leaf work TWICE --

      let (page_id, _) = self.find_leaf(key.clone())?;   // descends; deserializes the leaf
      let frame_i = self.buffer_pool.fetch_page(page_id)?; // fetches the SAME page again
      let leaf = BPlusTreeLeafPage::deserialize(frame.data)?;  // deserializes it again

  plus a key clone and a Vec<u32> path allocation on every point lookup. The latching rewrite
  replaced it with `read_leaf_for(key)`, which returns the leaf the descent already deserialized.
  The win is deleted duplicate work that happened to be removed in the same commit. A latch cannot
  make a read faster; attributing this to the latch would be a false mechanism.
