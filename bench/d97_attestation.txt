⚠ THE DEFLATION COMES FIRST, BECAUSE MOST OF THIS IS NOT NEW AND THE FILE SAYS SO.
Merkle trees (1979), hash-linked timestamping (Haber & Stornetta 1991), git's commit DAG,
Certificate Transparency (RFC 6962 / RFC 9162), ForkBase, Amazon QLDB, immudb, Trillian and
Dolt all already do this. The inclusion-proof path, the consistency subproof and both
verification algorithms in `attest.rs` are RFC 9162's, transcribed — not improved on.
**Verdict: ~95% adoption.** What is ferrodb's: a fork entry's `prev` is the PARENT branch's
head, so the chain mirrors the branch tree and a proof establishes ancestry rather than bare
membership; and `BranchId::generation` is inside both the digest and the linkage index, so a
recycled id slot cannot inherit the attested history of the branch reaped out of it. Neither
is research. A hash chain is forty-five years old and nothing here claims otherwise.

⚠ THE BRIEF ASKED FOR A HAND-ROLLED NON-CRYPTOGRAPHIC HASH. DECLINED, AND THE PREMISE WAS
FALSE. `src/provenance/sha256.rs` already exists: a dependency-free SHA-256 pinned against
FIPS 180-4's published vectors. `src/consensus/signing.rs` made this exact call for its HMAC
("reusing the validated implementation rather than introducing a second primitive that would
need its own evidence"). `Cargo.toml`'s `[dependencies]` is still empty, so the zero-dependency
constraint is met — by reuse rather than by adding a weaker second primitive to a module whose
entire subject is evidence. There is therefore no "not cryptographic" caveat to state; the
limits below are structural and have nothing to do with the hash function.

=== ⛔ WHAT AN ADVERSARIAL REVIEW FOUND THAT THE FORCED-FIRE SET DID NOT ==============

The first version of this work was 22 green tests and the numbers above. A review in a fresh
context that had never seen it being written found six real defects, three of them HIGH. They
are recorded here rather than quietly fixed, because the pattern is the point: **a self-written
forced-fire set inherits the assumption that caused the defect.**

 1. HIGH — `verify_chain`'s `Fork` arm skipped the per-branch link check, requiring only that
    `prev` be *some* attestation the log had produced. Relabelling entry k as a `Fork` pointing
    at entry k-2 EXCISED entry k-1 from the chain: nothing linked to it any more, so its content
    could then be edited freely and the walk still passed.
 2. HIGH — the LAST entry of every branch was freely editable, because nothing recomputes an
    entry's attestation unless a later entry links to it. **The original sweep ran
    `for victim in 0..11` on a 12-entry log and therefore excluded exactly the index that would
    have failed.** That is not bad luck; a loop bound written by the same person who wrote the
    code will tend to stop where the code stops working.
 3. HIGH — `heads` was keyed by the raw `u64` slot, dropping `generation`, so a recycled slot
    chained onto the reaped branch's head — the exact inverse of the property this file's header
    claimed. `generation` was in the DIGEST from the start; it was not in the STRUCTURE, and
    only the structure decides what links to what.
 4. MEDIUM — `verify_branch` returned `Ok(0)` for an absent branch, so a branch whose entire
    history had been deleted read as verified. A zero result is a fact about scope, not a pass.
 5. MEDIUM — both `verify_branch` failure paths reported `expected_prev: genesis`, a value
    neither of them ever expected, in the one type whose job is to locate the fault.
 6. MEDIUM — `verify_consistency` accepted a `size: 0` head carrying ANY root, all-zeroes
    included — precisely the value an uninitialised or truncated stored head takes.

Plus four smaller ones: a public `mth_range` that panicked on out-of-range input; a header
citing a test that did not exist; a documented attestation preimage that omitted
`branch.generation`; and `ENTRY_BYTES` asserting a decoder that had not been written (now
written, so the "a third party holds 85 bytes" story has something to parse them with).

Each fix carries a regression test that failed when written. 22 tests -> 31.

=== WHAT THIS DOES NOT CLAIM =========================================================

  * No signatures. A root proves WHAT the log said, never WHO said it. CT signs its tree
    heads; this does not. `consensus::signing` holds the HMAC that would.
  * Not durable. `AttestedHistory` is in memory. Who publishes heads, and where, is not here.
  * It binds content only as well as the caller's `content_cid` does. `ContentId` is
    constructible from bytes or an explicit digest and **there is deliberately no
    `ContentId::from_page_id`**: a chain over page NUMBERS would attest that a branch pointed
    somewhere and say nothing about what was there.
  * `BranchRecord` does NOT carry a `prev_attestation` field. D97 owns `attest.rs` and one
    line of `branch/mod.rs`; `record.rs` and its fixed-width `CORE_BYTES = 54` belong to other
    work in flight. The log is a separate structure that takes a record's fields as input.
