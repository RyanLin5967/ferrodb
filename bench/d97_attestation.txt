⚠ THE DEFLATION COMES FIRST, BECAUSE MOST OF THIS IS NOT NEW AND THE FILE SAYS SO.
Merkle trees (1979), hash-linked timestamping (Haber & Stornetta 1991), git's commit DAG,
Certificate Transparency (RFC 6962 / RFC 9162), ForkBase, Amazon QLDB, immudb, Trillian and
Dolt all already do this. The inclusion-proof path, the consistency subproof and both
verification algorithms in `attest.rs` are RFC 9162's, transcribed — not improved on.
**Verdict: ~95% adoption.** What is ferrodb's: a fork entry's `prev` is the PARENT branch's
head, so the chain mirrors the branch tree and a proof establishes ancestry rather than bare
membership; and `BranchId::generation` sits inside the digest, so a recycled id slot cannot
inherit the attested history of the branch that was reaped out of it. Neither is research.

⚠ THE BRIEF ASKED FOR A HAND-ROLLED NON-CRYPTOGRAPHIC HASH. DECLINED, AND THE PREMISE WAS
FALSE. `src/provenance/sha256.rs` already exists: a dependency-free SHA-256 pinned against
FIPS 180-4's published vectors. `src/consensus/signing.rs` made this exact call for its HMAC
("reusing the validated implementation rather than introducing a second primitive that would
need its own evidence"). `Cargo.toml`'s `[dependencies]` is still empty, so the zero-dependency
constraint is met — by reuse rather than by adding a weaker second primitive to a module whose
entire subject is evidence. There is therefore no "not cryptographic" caveat to state; the
limits below are structural and have nothing to do with the hash function.

A detector that has never rejected anything is not a clean result. Every line below is an
expectation the harness asserts and exits non-zero on; `exit=0` on all three repetitions.

  MUTATION DETECTED AND LOCATED. Entry 4's content digest altered in place; `verify_chain`

  ⛔ THE LIMIT, PROVED RATHER THAN ASSERTED. An adversary who alters entry 4 AND recomputes
  every later `prev` produces a chain that is internally perfect, and **`verify_chain` ACCEPTS
  IT**. The harness asserts that it accepts it, so the limit cannot quietly stop being true.
  The same rewrite fails a consistency proof against a head published before it. Truncation is
  in the same class: dropping the tail leaves a shorter valid chain, invisible to a walk.
  ⇒ **A deployment that never publishes a head anywhere gets the weak half of this and not the
  strong half.** The chain makes one record self-describing; only a witnessed (size, root)
  detects a rewrite of the past.

  NOT FIRING SPURIOUSLY. A legitimate 449-entry history over 64 agent branches verifies, all
  449 entries prove their own inclusion, and a legitimate 50-entry append still verifies
  against the head published before it.

=== TWO DEFECTS THE FORCED-FIRE TESTS FOUND, WHICH REVIEW HAD NOT ====================

 1. **`verify_inclusion` read `tree_size` out of the PROOF** — i.e. the untrusted prover
    supplied an input the algorithm authenticates against. Not theoretical: RFC 9162 folds the
    size in only through `sn`, which tracks the right-hand edge of the tree, so for a leaf away
    from that edge many sizes reduce identically. **Measured: at n=37, index 11, a proof
    relabelled n=38 verified against the n=37 root.** Fixed by `TreeHead`, which carries size
    and root as one value so a caller cannot hold a root without the size it belongs to.
    Caught by `inclusion_verification_refuses_every_way_a_proof_can_be_wrong` failing on its
    first run — the test was right and the verifier was wrong.

 2. **A `TamperFinding::HeadMismatch` arm that could never fire.** It compared
    `AttestedHistory::heads` against a re-derivation of itself by the same function. Removed
    rather than left as coverage that would be counted and could not fire.

=== WHAT THIS DOES NOT CLAIM =========================================================

  * No signatures. A root proves WHAT the log said, never WHO said it. CT signs its tree
    heads; this does not. `consensus::signing` holds the HMAC that would.
  * Not durable. `AttestedHistory` is in memory. Who publishes heads, and where, is not here.
  * It binds content only as well as the caller's `content_cid` does. `ContentId` is
    constructible from bytes or an explicit digest and **there is deliberately no
    `ContentId::from_page_id`**: a chain over page NUMBERS would attest that a branch pointed
    somewhere and say nothing about what was there.
  * `BranchRecord` does NOT carry a `prev_attestation` field. D97 owns `attest.rs` and one
    line of `branch/mod.rs`; `record.rs` and its fixed-width `CORE_BYTES = 54` belong to other
    work in flight. The log is a separate structure that takes a record's fields as input.
