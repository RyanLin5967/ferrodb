THE INSTRUMENT
--------------
No existing counter answers this. `scan_rows_observed` (runtime.rs:1042) was checked FIRST,
per the brief, and CANNOT fire on a merge: it is not a global counter but a per-workspace
field derived in `run_activity` (runtime.rs:1869-1897) by summing `p.rows_observed` over
ReadSet::Predicate entries in `state.captures[ws.txn]`. A merge's internal scans call
`scan_table(name, &ctx.read())` directly (runtime.rs:4367), which builds a plan in
`scan_table_where` (runtime.rs:6716) and drains it — recording nothing into `captures`.
Reported to the dispatcher as: does not fire, new counter required.

Two counters are added, both following the repo's own pattern and its cardinal rule stated
at runtime.rs:115 — count PER SCAN, one relaxed fetch_add, "so the instrument cannot create
the slope it measures":

  A. SCAN_TABLE_CALLS / SCAN_TABLE_ROWS  (src/agent_sql/runtime.rs, beside OURS_SCAN_*)
     One relaxed fetch_add per `scan_table_where` call, of `out.len()`. Rows RETURNED.

  B. SEQ_SCANS / SEQ_SCAN_TUPLES  (src/execution/seq_scan.rs)
     Tuples pulled from the heap by a SeqScan. Accumulated in a plain non-atomic local
     field and flushed with ONE relaxed fetch_add in `Drop`.

  Why B is not optional. A is rows RETURNED. The point-lookup path (runtime.rs:4421) pushes
  `pk = k` into the planner and returns ONE row. If the planner does not pick an index and
  degenerates to a sequential scan, the engine reads O(table) while A reports 1 — a flat A
  curve produced by an O(table) merge. That is a non-discriminating falsifier, and B is what
  discriminates it. A count that is flat in A AND flat in B is a real O(delta) merge; flat in
  A while B grows is the claim surviving underneath a blind instrument.

Scoping: both are process-global. Read twice and subtract around the phase, which is the
pattern `ours_scan_counters` documents at runtime.rs:1036. The harness is SINGLE-THREADED
so the subtraction is exact.

AMENDMENT 1 — ARM D added AFTER the first run. Declared here because it was.
-----------------------------------------------------------------------------
The first run (raw kept at bench/d176_rowcount_RAW.txt) produced, for ARM A:

    nrows   rows/merge   tuples/merge
      500            4           2000
     1000            4           4000
     2000            4           8000
     4000            4          16000

rows is FLAT, which is F1. tuples is 4n — LINEAR IN TABLE SIZE — which is P5, the
pre-registered case in which F1 does NOT hold and the flat rows curve is an artifact of
counting rows returned. At delta = 4 the merge issues 4 point lookups and each one pulls
the ENTIRE table off the heap. ARM C confirms the second axis: at n = 2000, tuples run
2000, 4000, 8000, 16000, 32000, 64000 for delta 1..32 — exactly delta * n.

So P1 is WRONG as I wrote it, P5 fires, and the claim survives rather than dying. That is
recorded here rather than quietly rewritten, because the pre-registration is only worth
something if a prediction that failed stays visible.

⛔ BUT P5 FIRING IS NOT YET A RESULT, because the fixture may be the cause. `build_sized`
creates `t (id INTEGER NOT NULL, v INTEGER)` with NO INDEX on `id`. The merge's point
lookup pushes `id = k` into the planner (D55), and a pushed predicate with no index to
pick can only become a sequential scan. A table with no index is exactly the fixture in
which every point lookup looks O(table) whether or not the merge is at fault.

  ARM D — plain MERGE, same size axis, same fixed delta, against
          `CREATE INDEX ix ON t (id);` built after the inserts and ANALYZE'd.

  D1. If ARM D's tuples/merge COLLAPSES (flat, or growing far slower than n), then ARM A
      measured MY SCHEMA and not the merge. The honest claim is then narrow: merge is
      O(delta * table) ON A TABLE WITH NO INDEX ON THE LOOKUP COLUMN, and on an indexed
      table it is O(delta * log n). That is a much weaker statement and it will be
      reported as the weaker one.
  D2. If ARM D's tuples/merge still grows ~linearly in n, the merge cannot use the index
      and the finding is about the MERGE. O(delta * table) stands unqualified.

No other arm, prediction or falsifier is changed. F4 (the fire-check) already passed on
