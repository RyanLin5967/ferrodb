⭐ THE ARM ORDER IS ROTATED TOO, AND IT MATTERED.
   The first run measured the SAME configuration -- one thread on servers[0] -- at 52187
   stmt/s as arm A's baseline and 23341 as arm B's. A 2.2x gap for identical work.
   Rotating POINTS within a round cannot cancel a bias sitting between ARMS. Running the
   control FIRST put arm A's 1T at 28530 and arm B's at 24046 -- so 52187 was the outlier,
   an artifact of arm A running first on a freshly started process, and it would have
   inflated arm A's baseline and made a FLAT curve read as a DECLINING one.

BOTH ORDERS, ON THE ABSOLUTE TOTALS (which need no baseline at all):

                          A-then-B run      B-then-A run
  arm A (shared)  1T          52187             28530
  arm A (shared) 16T          46897             23074      <- FLAT. 15 more threads, no gain.
  arm B (control) 1T          23341             24046
  arm B (control)16T         174247            134571      <- RISES 5.6x-7.5x
  apart at 16T                 3.72x             5.83x

ARM A'S TOTAL IS FLAT IN BOTH ORDERS (total_vs_1T at 16T: 0.899 and 0.809). That is the
signature of one statement at a time: total throughput is capped at the single-threaded
rate whatever N is. The control, which removes ONLY the shared Mutex<Catalog>, scales.

⭐ AND THE SIGNATURE DIFFERS FROM TURSO'S IN A WAY WORTH KEEPING:
     turso shared, 16T:   x0.308 of its 1T   -- WORSE than flat
     ferrodb shared,16T:  x0.809-x0.899      -- flat
   A clean global mutex hands off and stays flat. A contended SHARED lock is worse than
   flat, because the readers pay cache-line ping-pong on top of serializing: turso's 16
   readers do LESS total work than one. Same wall class for the objective -- concurrent
   agents get no concurrent statements -- but not the same curve, and the difference is
   the cost of pretending a shared lock is cheap.
