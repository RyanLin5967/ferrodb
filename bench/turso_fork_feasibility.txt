5. ⭐ THE FINDING THAT MATTERS, AND IT REFUTES MY OWN PROPOSED WALL
-------------------------------------------------------------------
  I proposed (D47 section 3) that turso inherits SQLite's read-mark cap and that it binds
  branch-per-agent: slots 1-4 carry a frame number, so at most FOUR DISTINCT snapshot
  positions can be pinned at once, and `begin_read_tx` returns Busy after ~100 retries of
  quadratic backoff rather than queueing. That is structurally MAX_BRANCH_DEPTH = 8 in a
  real engine, which is exactly the kind of cap the objective wants found.

  [HERE]  wal.rs:2821-2828   "Slots 1-4 carry a frame-number in value and may be shared
                              by many readers"                           -> the cap is on
                              DISTINCT positions, not on readers. Confirms the reading.
  [HERE]  wal.rs:874-880     min_read_mark iterates `for slot in 1..5`   -> same four.
  [HERE]  wal.rs:3310-3345   begin_read_tx: Busy after cnt > 100, quadratic backoff,
                              comment says it mirrors SQLite deliberately.

  ⛔ AND THEN IT DOES NOT HOLD, because turso has a second mechanism:

  [HERE]  shared_wal_coordination.rs:143,147   fn new(reader_slot_count: u32) ->
                                               reader_owners: vec![None; reader_slot_count]
  [HERE]  shared_wal_coordination.rs:399,446   reader_slot_count is a u32 FIELD of the
                                               on-disk coordination header, not a constant
  [HERE]  wal.rs:7133                          a test opens one with 64 slots
  [HERE]  core/build.rs:9                      host_shared_wal: { all(any(unix, windows),
                                               target_pointer_width = "64") }

  ⇒ `host_shared_wal` is a PLATFORM cfg, not an opt-in feature. On any 64-bit unix or
    windows host — which is every machine this would run on — the parameterised coordination
    layer is compiled in. So the four-slot array is the SQLite-file-format path, and turso
    ALREADY HAS a slot count that is a parameter rather than a constant.

  VERDICT ON MY OWN PITCH: the wall as I stated it is WITHDRAWN. This is prior art inside
  the target, which D47 itself named as the strongest possible kill, and it was found by
  reading for twenty minutes instead of by porting for a week. What survives is narrower
  and still worth one measurement: 64 is a parameter but it is still a number, and nobody
  has shown what happens to it at 10^3 readers, let alone 10^6. That is a question about a
  constant, which is the lowest-value shape this project recognises -- so it does NOT get a
  pass on its own. It gets recorded here so the next session does not re-derive the dead
  half.
