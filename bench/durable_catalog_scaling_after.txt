AFTER: bytes DOUBLE when N doubles, so the log is O(N). 68 bytes per branch.
   8000 branches: 257,120,000 -> 544,000 bytes, a 473x reduction; reopen 0.766s -> 0.002s.
   Extrapolated at 10^6 branches: ~4TB -> ~68MB.

The fix is not a smaller record. `live_children` is no longer STORED at all - it is derived at
replay from the children that name the parent, so `fork` appends the child alone. The array was
always redundant: a child record already carries `parent_id` and `fork_epoch`.

It also closes the correctness hole it used to trade against. `fork` wrote child and parent under
one fsync because a child durable without its parent's entry is a page nobody knows to park.
Derived, the child record IS the parent's entry, so the two cannot disagree.

Per-fork latency is unchanged (~3-4ms, fsync-bound) - as before, this wall was never visible in a
latency measurement.
