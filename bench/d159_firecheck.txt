FIRE-CHECK 2 — THE SAFETY NET, after review found the first guard could not fire
=================================================================================================
HEAD eabff0f. An adversarial review (reviewed at `2028de8`) found that `ForkDurability`'s original
enforcement was **two guards that could not fire**, which is this project's standing trap:

  * `#[must_use]` fires on an unused EXPRESSION. All three call sites BIND
    (`table_catalog.rs` `let (record, seq) = …`, `runtime.rs` `let (session, durability) = …`,
    `dispatch.rs` `let (s, durability) = …`), so the lint was always satisfied, and
    `let (s, _) = …` would have defeated it silently.
  * The `Drop` check was `debug_assert!`. VERIFIED HERE: `Cargo.toml` has **no `[profile]`
    section** (`grep -n '^\[profile' Cargo.toml` -> no match) and there is **no `.cargo/`
    directory**, so `--release` means `debug-assertions = false`. d130's artifact header reads
    `Finished 'release' profile`. ⇒ The assertion did not exist in the binary that serves pgwire.

FIX: `Drop` now DISCHARGES the obligation — it performs the sync — so "staged but never synced" is
unrepresentable rather than asserted against. `session::fallback_syncs()` is a plain atomic that
counts the net's use and works in release.

FIRE-CHECK 3 — ⭐ EVERY SYNC-COUNTER TEST PASSES WHILE THE DATA IS GONE
=================================================================================================
HEAD a0bcbbc. The "a staged fork cannot be lost" argument does NOT rest on the per-seq ticket
accounting this design is written in terms of. It rests on something coarser: `durable(seq)` calls
`BufferPoolManager::flush_all`, which **takes no seq** and writes every dirty page. So any later
sync on the catalog flushes a fork that was staged and never awaited.

From inside `durable()` that reads like dead work — the method HAS a `seq`, so why flush pages no
ticket asked for? This fire-check answers that.

THE MUTANT — the plausible "optimisation", one line
    self.commit_group.wait_durable(seq, || {
        // self.pool.flush_all()?;        <- removed
        self.pool.disk_manager.sync()
    })

⛔ **READ THE PASSING COLUMN, NOT THE FAILING ONE.** Six of seven pass — including
`two_forks_staged_before_either_completes_share_one_fsync`, which is the headline evidence for this
whole row, and `dropping_..._still_syncs_and_is_counted`, which is the safety net's own proof.
**Under this mutant the branch catalog loses every staged fork, and both of those still read green,
because `CommitGroup` reports the fork durable while its pages were never written.**

⇒ ⭐ **A SYNC COUNT IS NOT A FACT ABOUT THE DISK.** Every assertion in this file except one is on
`syncs_issued()`, an in-process counter, and a counter cannot see an unwritten page. The only test
that catches this asserts against the FILE — it reopens `{db}.branchcat` with `open_sidecar` and
demands the record back. That is the difference between instrumenting the mechanism and checking
the outcome, and it is the reason this test was added rather than trusting the five that were
already green.

⚠ Consequence for anyone editing `durable()`: narrowing `flush_all` to a seq-scoped flush converts
a non-hazard into a real one, and the suite would have told you it was fine. The warning is on
`durable()` itself, where the edit would be made, not only here.

STATED BLIND SPOTS
------------------
* This proves the MECHANISM batches. It does not prove any CLIENT sees a batch — that needs the wire
  measurement, and D159 amendment 4 predicts, in advance, that `f/sync` stays near 1.00 on
  `examples/d130_pgwire_batch.rs` because that harness gives every fork a unique run id and so pays
  `prov_store.intern`'s own ungrouped fsync per fork, under `state`, inside the catalog guard.
* One mutant, at one site. It does not exercise the A/B-atomicity argument (SCALE-DESIGN D159
  amendment 1), which is a claim about what stays INSIDE the guard and is not expressible as a sync
  count.
* ⛔ **This bullet used to read:** *"Debug build. `ForkDurability`'s `Drop` assertion is a
  `debug_assert!` and is compiled out of release, so the 'staged and never awaited' guard is a
  test-time guard, not a production one."* **It was written as a blind spot and it was actually a
  DEFECT** — stating a guard's weakness in the guard is the right habit, but the correct response
  to "this guard does not exist where it matters" is to fix it, not to log it. Fire-check 2 above
  is that fix, and the release run is its evidence. Kept rather than deleted, because a blind spot
  that turned out to be a defect is the more useful record.
* A failed fallback sync inside `Drop` still cannot be reported — `Drop` has nowhere to put an
  error. It is only reachable on a path that already forgot `complete()`, and it is counted.
* `fallback_syncs()` is process-wide, so the two tests that read it take a mutex. That makes them
  correct under cargo's parallel harness; it does not make the counter per-catalog, so a future
  test that trips the net without taking that mutex could perturb them.
