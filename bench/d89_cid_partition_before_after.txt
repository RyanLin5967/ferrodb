⚠ CORRECTION, logged where the claim was made. An earlier version of this section read "the
instrument's reach is now: a cid compares two trees holding the same rows exactly, however those
rows were reached." That is FALSE and was falsified by adversarial review
(artie-research/frontier/review-chunker.md F1, probe a9 at review-chunker-attack 5e13e98),
reproduced here against both trees before being written down:

                                   main 1758b3b                 with unlink_up
    suffix, delete 500..1000    44 leaves, 22 empty, agree    22 leaves, 0 empty, agree
    one interior boundary key   44 leaves,  0 empty, DISAGREE 44 leaves, 0 empty, DISAGREE

    interior case, first disagreeing surviving leaf: churned 28 rows / clean 37 (neither empty)
      churned live leaf sizes [28, 28,  9, 16]
      clean       leaf sizes  [28, 37, 16,  6]

The interior-key row is byte-identical either side of the fix, because no leaf is emptied there
and so there is nothing to unlink. Deleting the key that TERMINATES a leaf destroys that leaf's
content boundary; the leaf and its right neighbour stay split where the chunker would cut one
(28 + 9 = 37). Repairing that is a neighbour merge, which needs the sibling access this layout
deliberately lacks — the thing the pre-registered diagnosis explicitly ruled out.

A contiguous suffix is the ONE delete shape that cannot expose this, because the only terminator
it destroys belongs to the last leaf, and the last leaf may end anywhere. The fixture picked that
shape, so it returned the calm answer and the diagnosis read it as the whole story. That is the
same fixture-scope defect the insertion-order test above was built to avoid, appearing in the test
written to replace it.

So the corrected reach: a cid compares two trees built by insertion exactly, and two trees whose
histories differ by a delete only when the delete destroyed no interior boundary. The rest is
cow::cid::tests::a_delete_of_an_interior_boundary_key_must_not_change_the_partition, #[ignore]d,
and it needs a merge rather than another unlink.

An internal node holds a leftmost child plus `count` slots, so removing a slotted child always
leaves the leftmost behind; a node becomes childless in exactly one case, when the removed child
was the leftmost and count was 0. That single case is the whole cascade condition, which is why it
terminates in tree depth and needs no rebalance. Pages are freed only after the parent has stopped
pointing at them — free_page can hand a page straight back to the free map, so the other order
leaves a live parent pointing at a page an allocator may have reissued.

It does NOT merge half-empty siblings or collapse a root left with one child. Both are rebalancing,
both need the sibling access this layout deliberately lacks, and neither is needed for the partition
to be a function of the rows.

Measured effects of the fix:

    live pages after deleting every key of 1000: 45 -> 1   (pages freed, not merely unlinked)
    cargo test --lib, D104 tip 913e53f: 1548 passed; 0 failed; 2 ignored; finished in 86.93s
    cow::btree::delete_unlink_tests: 7 passed; 0 failed

Seven tests were added because CowTree::delete had almost no direct coverage to break — one diff
test used it and nothing else. The two that would catch this going wrong are
every_surviving_key_is_still_readable_after_scattered_deletion (point lookups AND an ordered scan,
because a broken separator shows up only in the scan) and
deleting_on_a_fork_leaves_the_parents_tree_intact (a child freeing a page its ancestor still points
at would corrupt the ancestor, in the wrong branch, silently).


=== Adversarial pass ===

Branch D89-falsify, commit 3c2a132, attacked the BEFORE measurement in a fresh context
(examples/d89_falsify.rs, d89_falsify2.rs; raw output in bench/d89_falsify_raw/). It confirmed the
instrument — no PageId/epoch/arena leak under 6 physical conditions, the control fires when the
data really differs, the shared-leaf statistic equals a true LCS in all 1016 sweep rows — and
falsified the doc comment's GENERALISATION, which claimed convergent lineages never share subtrees.
At 990-byte values or near-sorted orders, sharing already survived pre-chunker. That over-broad
sentence is gone; the module now states its reach as a measured boundary rather than a slogan.

It also showed leaf_partition_cid is blind to tree height and separator keys: two well-formed trees
over the same leaves, one height 2 and one height 3, answering get() identically on all 312 keys,
share a partition cid (c43e68de...) while their subtree_cids differ (903bcc9b... vs ecc07373...).
By construction, and now documented on leaf_partition_cid — compare trees for sameness with
subtree_cid, not with the partition cid.
